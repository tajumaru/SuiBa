# ダッシュボード閲覧経路の Tailscale 移行設計書 ― WireGuard 自作構成から Tailscale Serve（HTTPS）へ

- 作成日：2026-11-11
- ステータス：設計のみ（未実施）。実施は たじゅまる の別途判断。本書は「手順・設計を作って欲しい」という依頼に基づく
- 対象：さくら VPS 上の Potario ダッシュボード（Worker が `127.0.0.1:3100` で待ち受け）を、たじゅまる の iPhone から閲覧する経路のみ

---

## 1. 目的と範囲

### 1.1 目的

ダッシュボードの閲覧経路を、現在の手組み WireGuard トンネル（平文 HTTP）から **Tailscale Serve による HTTPS** に替える。これにより、非セキュア文脈（`http://` の非 localhost アドレス）に起因する問題の「クラス全体」を消す（§2.2）。Tailscale は WireGuard を土台にした市販の仕組みであり、トンネルの設置・鍵交換・名前解決を自動化したもの、と位置づける。自作 WireGuard の「置き換え」ではなく「業者版への載せ替え」である。

### 1.2 範囲（不変条件）

1. **替えるのは閲覧経路だけ**。Bot 本体（Worker・戦略・記録）、配置ブローカーと GitHub Actions の配置経路、監視（本番モニター・watchdog・日次レビュー）、本番運用の手順は一切変更しない。
2. **さくら VPS はそのまま**。引っ越しはしない。VPS に Tailscale クライアント（tailscaled）を追加で入れるだけである。
3. **ダッシュボードのコードは変更しない**。Worker の待ち受け（`127.0.0.1:3100`）も変更しない。Serve はその手前で TLS を終端する中継であり、アプリ側は同一オリジンのまま動く前提で、実施時に §5.5 の確認で担保する。
4. **Funnel は使わない**（§3.2）。インターネットへの公開は行わない。
5. **移行期間中は現行 WireGuard を残し併用可能**とする。切り戻しは §5.6 のとおり即時に可能で、WireGuard の撤去判断は移行後に分ける（§7）。

### 1.3 用語

| 用語 | 意味 |
|---|---|
| tailnet | Tailscale のアカウントに紐づく私設ネットワーク。参加には IdP（Google / GitHub 等）認証が要る |
| MagicDNS | tailnet 内の名前解決。マシンに `<マシン名>.<tailnet名>.ts.net` の名前が付く |
| Tailscale Serve | ローカルの待ち受けを tailnet 内だけに HTTPS で公開する機能。証明書は Let's Encrypt のものを Tailscale が自動取得・更新する |
| Tailscale Funnel | 同じ仕組みで対象を公共インターネットに公開する機能。**本設計では使用禁止**（§3.2） |
| tailscaled | 各マシンで動く Tailscale のデーモン／クライアント |
| CT ログ | Certificate Transparency の公開台帳。HTTPS 証明書を有効化するとマシン名と tailnet 名がここに記録される（§4.3） |

## 2. 現行構成と問題点

### 2.1 現行構成（2026-11-11 実測）

| 項目 | 現行 |
|---|---|
| 経路 | iPhone WireGuard アプリ → トンネル「SuiBa VPS」→ VPS の wg-suiba インターフェース |
| サブネット | `10.77.31.0/24`（VPS `10.77.31.1`、iPhone `10.77.31.2/32`、AllowedIPs は VPS のみ） |
| サーバー | `ik1-111-62314.vs.sakura.ne.jp`、UDP 21820 で待ち受け、keepalive 25 秒 |
| 中継 | VPS 上の systemd ソケットが `10.77.31.1%wg-suiba:3100` で受け、Worker の `127.0.0.1:3100` へ中継 |
| URL | `http://10.77.31.1:3100` |
| 自動接続 | オンデマンドは携帯回線のみ。自宅 Wi-Fi では WireGuard アプリで手動 ON が要る |

### 2.2 問題点

1. **非セキュア文脈の制約が恒常的に刺さる**。`http://10.77.31.1` はブラウザから見て非セキュア文脈のため `crypto.subtle` が存在しない。ダッシュボードはデータ取得の digest 照合に `crypto.subtle.digest` を使っていたため、**2026-11-11 夜に実際に障害として出た**（スマホでのみ赤バナー「チャート・履歴の更新に失敗しました」が常駐し、チャートと履歴が更新されない。Windows の localhost では再現しない）。PR #192 で純 TypeScript の SHA-256 フォールバックを入れて回避したが、これは対症療法である。
2. **同じ理由で使えない Web 標準機能がある**。Service Worker と PWA（ホーム画面アプリ化・殻のキャッシング）はセキュア文脈が前提のため、この経路では原理的に使えない。アクセス速度の改善（PR #196〜#199）を進めるほど、この天井が見えてくる。
3. **経路が細く詰まりやすい**。2026-11-11 夜、4G 経由でページ読み込みが途中で止まる症状が実発生した（Bot 本体はモニター観測で正常稼働を確認済み。閲覧経路側の問題）。手組みトンネルは MTU 等の調整も全て自前になる。
4. **運用の手間**。自宅 Wi-Fi では手動トグルが要る（§2.1）。鍵・アドレス・AllowedIPs の管理も全て手作業。

### 2.3 移行で期待する効果

- URL が `https://<マシン名>.<tailnet名>.ts.net` になり**セキュア文脈が成立**する。`crypto.subtle` が native で使えるようになり、§2.2-1 の障害クラスが消える（フォールバック実装は残してよい。害はない）。
- Service Worker / PWA が原理的に可能になる（導入自体は別判断）。
- トンネルの確立・維持・名前解決を Tailscale に任せ、手動トグルと鍵管理が消える。自宅 Wi-Fi／携帯回線のどちらでも同じ URL で開ける。

## 3. 移行後の構成

### 3.1 構成図

```
┌── たじゅまる の iPhone ──────────────┐   ┌── Windows PC（任意）──┐
│ Tailscale アプリ（VPN として常駐）    │   │ Tailscale クライアント │
│ Safari: https://<VPS>.<tailnet>.ts.net │   │ ブラウザ: 同じ URL     │
└──────────────┬───────────────────────┘   └──────────┬────────────┘
               │  tailnet（WireGuard 暗号化・端末間は直通が基本）
               ▼                                      ▼
┌── さくら VPS（ik1-111-62314.vs.sakura.ne.jp、Ubuntu・変更なし）──┐
│ tailscaled                                                        │
│   └─ Serve: tailnet の 443 で TLS 終端（Let's Encrypt 証明書）     │
│        → http://127.0.0.1:3100 へ中継                             │
│ Worker（コンテナ）: 127.0.0.1:3100 で待ち受け（変更なし）          │
│ Bot 本体・broker・監視：変更なし                                   │
│ （移行期間中は現行 wg-suiba ＋ systemd ソケット中継も併存）        │
└───────────────────────────────────────────────────────────────────┘
```

要点：

- Serve は **tailnet 内の端末からだけ**到達できる。インターネット側からは名前解決も接続もできない。
- 証明書の取得・更新は Tailscale が自動で行う。証明書ファイルの配置や更新 cron は要らない。
- VPS 側の変更は「tailscale パッケージの導入」と「serve 設定 1 件」だけ。Worker・broker・コンテナには触らない。

### 3.2 Funnel は使わない

Funnel は同じ URL を公共インターネットに公開する機能で、tailnet 参加なしに誰でも到達できるようになる。本設計の目的（自分だけが安全に見る）とは正反対なので、**有効化しない**。実施手順にも Funnel のコマンドは含めない。万一 `tailscale funnel status` に何か出ていたら異常として扱う（§5.5）。

### 3.3 Headscale（自前コントロールサーバー）について ― 検討して見送り

Tailscale の調整サーバーを自前で運用する Headscale という選択肢もあるが、調整サーバー自体の保守（更新・障害対応・バックアップ）が新たな運用対象として増える。現行規模（利用者 1 人・端末数台）では Personal 無料枠で足りる（§8）ため、**今回は見送り**、将来 Tailscale 側の条件が変わった場合の退避先として名前だけ残す。

## 4. セキュリティ設計

### 4.1 到達可能性

- 公開範囲は **tailnet 内限定**（§3.2）。tailnet への参加は IdP アカウントの認証が前提で、端末は管理コンソールで一覧・失効できる。
- VPS の既存の公開面（SSH・broker・WireGuard 21820/udp 等）は本移行で**増やさない**。Serve は tailscaled が tailnet アドレスで受けるもので、VPS のパブリック IP に新しい待ち受けを作らない。

### 4.2 認証は多層のまま

1. **tailnet 参加**：IdP アカウント認証（たじゅまる のアカウント）。アカウント側で二要素認証を有効化しておくことを前提とする。
2. **ダッシュボードのログイン**：既存のログイン認証はそのまま存続させる。Serve は認証を肩代わりしない、素通しの中継である。どちらか一方が破れても、もう一方が残る構成を維持する。

### 4.3 正直に書いておく点

- HTTPS 証明書を有効化すると、**マシン名と tailnet 名が CT ログに公開記録される**（Let's Encrypt の仕様）。名前を知られても到達には tailnet 参加と認証が必須であり、実害は小さいが、「名前は公開情報になる」ことは承知のうえで有効化する。気になる場合はマシン名に意味のある文字列を使わない。
- Tailscale の調整サーバー（鍵交換・ACL 配布）は Tailscale 社の運用に依存する。通信そのものは端末間の WireGuard 暗号化であり、調整サーバーが本文を読むことはないが、可用性は同社のサービスに依存する。この依存が嫌な場合の退避先が Headscale（§3.3）と現行 WireGuard（§5.6）である。

### 4.4 触れないもの

- SSH 経路（配置用・管理用・観測用の各 identity）と broker の固定 op には一切触れない。**Tailscale SSH（`--ssh`）は有効化しない**。
- ACL は **既定（同一 tailnet 内・所有端末間の許可）から開始**する。絞り込みは必要になった時点で別途設計する。最初から ACL を書き込まない（書くほど壊す面が増える）。
- 認証情報の扱い：ログインはブラウザ経由の対話式で行い、auth key をコマンド引数・ファイル・チャットに残さない。
- VPS ノードのキー有効期限：既定では期限切れで tailnet から外れる。無人サーバーでは管理コンソールで当該マシンのキー期限を無効化できるが、それは「失効させるまで恒常的に参加し続ける」ことと引き換えである。どちらにするかは §7 の未決事項とする（実施手順では既定のまま進め、判断を先送りできる形にする）。

## 5. 実施手順（ランブック）

前提の位置づけ：VPS への tailscale 導入は broker の固定 op の範囲外のホスト作業であり、過去の setup スクリプト実行と同様、**たじゅまる がターミナルで実行する**。以下はその逐語手順である。本番（Bot）は稼働したまま実施する想定で、Bot・コンテナ・broker には触らない（実施可否の整理は §7）。

### 5.1 事前作業（ブラウザ・管理コンソール）

1. Tailscale アカウントを作成する（IdP の選択は §7 の未決事項。ここでは選んだ IdP でログインできるところまで）。
2. 管理コンソール（`https://login.tailscale.com/admin`）の **DNS** ページで次を有効化する：
   - **MagicDNS**：有効化
   - **HTTPS Certificates**：有効化（§4.3 の公開記録の注記が出るので承知のうえで進める）
3. この時点で tailnet 名（`*.ts.net` のサフィックス）が決まる。VPS のマシン名とあわせて §5.5 の確認 URL が確定する（実際の名前は実施時に記録する）。

### 5.2 VPS 側（ターミナル）

公式の Linux 導入手順に従う。ホストの DNS 設定を変えないため `--accept-dns=false` を付ける（VPS 自身の名前解決は broker や配置経路が使っており、本移行の都合で触らない）。

```bash
# 1) インストール（公式 install スクリプト。apt リポジトリが登録される）
curl -fsSL https://tailscale.com/install.sh | sh

# 2) tailnet に参加（表示される URL をブラウザで開いて認証する）
sudo tailscale up --accept-dns=false

# 3) 参加できたことと自分の名前・アドレスを確認
tailscale status
tailscale ip -4

# 4) バージョン確認（serve の現行構文は 1.52 以降のもの。本書のコマンドはそれ前提）
tailscale version
```

次に Serve を設定する。**`--bg` を付けると設定が tailscaled の状態として保持され、ターミナルを閉じても・再起動しても有効**になる。

```bash
# 5) ダッシュボードを tailnet 内に HTTPS で公開（443 → 127.0.0.1:3100）
sudo tailscale serve --bg --https=443 http://127.0.0.1:3100

# 6) 設定の確認（https://<マシン名>.<tailnet名>.ts.net が
#    「proxy http://127.0.0.1:3100」と出ること）
tailscale serve status
```

注意点：

- 初回の `serve` 実行時に、tailnet 側で Serve 機能の有効化を求める URL（`https://login.tailscale.com/f/serve?...`）が表示されて待つ場合がある。その場合は URL を開いて有効化し、同じコマンドを再実行する（**要実地確認**：表示の有無は tailnet の状態による）。
- 証明書の初回取得には少し時間がかかることがある。`serve status` が出ても最初のアクセスで数秒待つ場合は、少し置いて §5.5 をやり直す。
- `sudo` の付かない `tailscale serve status` は参照のみ。変更系は `sudo` を付ける（運用ユーザーを operator に登録する方法もあるが、本書では sudo 形に統一する）。

### 5.3 スマホ側（iPhone）

1. App Store から Tailscale アプリを入れ、§5.1 と同じ IdP アカウントでログインする。
2. アプリ側で VPN を ON にする（iOS の VPN 許可ダイアログを承認）。
3. Safari で `https://<マシン名>.<tailnet名>.ts.net` を開く（ポート番号は不要。443 が既定）。
4. §5.5 の確認を行う。

注意点：iOS では有効化できる VPN 構成は同時に 1 つだけなので、**Tailscale を ON にすると WireGuard トンネルの接続は切れる**（構成自体は残る）。移行期間中の行き来は「どちらの VPN を ON にするか」で切り替える。携帯回線でも自宅 Wi-Fi でも同じ操作・同じ URL で開けるのが移行後の姿である。

### 5.4 Windows PC（任意）

自宅 PC からも見たい場合のみ。公式インストーラ（`https://tailscale.com/download/windows`）を入れて同じアカウントでログインし、ブラウザで同じ HTTPS URL を開く。それ以外の変更は PC 側にも不要。

### 5.5 確認手順（チェックリスト）

VPS 側：

- [ ] `tailscale serve status` に目的の URL と `proxy http://127.0.0.1:3100` が出ている
- [ ] `tailscale funnel status` に何も出ていない（Funnel が誤って有効になっていない）
- [ ] 本番モニターの観測が平常どおり `ok` で、Bot の稼働に影響が出ていない

スマホ側：

- [ ] HTTPS URL が**証明書エラーなし**で開ける（鍵マークが正常）
- [ ] ダッシュボードにログインできる
- [ ] **赤バナー「チャート・履歴の更新に失敗しました」が出ない**（＝digest 照合が native の `crypto.subtle` で通っている）
- [ ] チャートと履歴が更新される。価格・チェーン行も更新される
- [ ] 携帯回線と自宅 Wi-Fi の両方で、VPN の手動切り替えなしに開ける（Tailscale ON のまま）

併用確認：

- [ ] WireGuard 側の VPN に切り替えれば、従来 URL `http://10.77.31.1:3100` でも従来どおり開ける（切り戻し可能性の実証）

### 5.6 切り戻し手順

いずれも即時で、Bot・本番運用には影響しない。旧 WireGuard 経路は移行期間中ずっと生きている。

```bash
# Serve だけを止める（HTTPS 公開をやめる。tailnet 参加は維持）
sudo tailscale serve --https=443 off

# Serve 設定を全て消す場合
sudo tailscale serve reset

# tailnet 自体から一時的に抜ける場合
sudo tailscale down
```

スマホ側は VPN を WireGuard「SuiBa VPS」に切り替えれば、その時点で従来どおり `http://10.77.31.1:3100` に戻る。Tailscale のアンインストールは切り戻しには不要（恒久撤去の判断は §7）。

## 6. 影響を受ける資産（移行実施時の作業）

| 資産 | 実施時の作業 |
|---|---|
| Potario ランチャー（Space） | 「Potario を開く」ボタンのリンク先を `http://10.77.31.1:3100/` から新しい HTTPS URL へ差し替える。案内文（WireGuard を ON にする手順）も Tailscale 前提に書き換える |
| WireGuard 閲覧手順メモ（workspace の手順書） | 本書＋実施結果をもって後継とし、旧手順は履歴として残す（WireGuard 撤去までは切り戻し手順として有効） |
| Potario 運用ボード | 閲覧 URL の記述を HTTPS URL に更新する |
| 運用メモ類（MEMORY 等の URL 記載） | 閲覧 URL の記載を新しい URL に更新する。旧 URL は切り戻し用として併記を残す |

ダッシュボード・Worker・broker のコード変更は不要（§1.2-3）。seq の配置も不要（ホスト側のみの変更であり、イメージには含まれない）。

## 7. 未決事項

| # | 項目 | 整理 |
|---|---|---|
| 1 | IdP の選択 | Google / GitHub / Apple 等から選ぶ。既に日常使っているアカウントに寄せるのが運用は楽だが、二要素認証の状態も含めて たじゅまる が決める |
| 2 | tailnet 名・マシン名 | tailnet 名はアカウント作成時に決まる（後から変更は可能だが URL が変わる）。マシン名は CT ログに残る（§4.3）ため、意味を持たせすぎない名前を推す。実施時に確定し、本書の実施記録として残す |
| 3 | VPS ノードのキー期限 | 既定（期限あり・再認証が必要）と、コンソールで期限を無効化（無人運用向きだが恒常参加）のどちらにするか（§4.4） |
| 4 | WireGuard 撤去の判断時期 | 移行後しばらく併用し、HTTPS 経路で困らないことを確認してから別途判断する。撤去する場合は wg-suiba・systemd ソケット中継・ファイアウォールの 21820/udp をまとめて外す設計が別に要る |
| 5 | 実施タイミング | **本番稼働中の実施は可能**と整理する。理由：変更対象はホストの追加パッケージと tailscaled の待ち受けのみで、Worker コンテナ・broker・配置経路に触らず、ホスト DNS も `--accept-dns=false` で不変。失敗時は §5.6 で即時に従来経路へ戻れる。ただし初回は、本番モニターの定常観測が見える時間帯に、§5.5 をその場で完走できる形で行う。実施日時は たじゅまる が決める |
| 6 | PWA / Service Worker の導入 | HTTPS 化で「可能」にはなるが、導入するかは別判断（本書の範囲外） |

## 8. 費用

- Tailscale **Personal プランは無料**（2026-11-11 に公式 pricing で確認：利用者 6 人まで、ユーザー端末は無制限、タグ付きリソース 50 個まで）。本構成は利用者 1 人・端末 3 台（VPS・iPhone・任意で Windows PC）で、枠内に十分収まる。
- 有料プラン（Standard $8/ユーザー/月〜）は事業者・チーム向けであり、本用途では不要。
- 価格・枠は将来変わりうる。変わった場合でも、切り戻し（§5.6）と Headscale（§3.3）の退避先があるため、ロックインは浅い。
