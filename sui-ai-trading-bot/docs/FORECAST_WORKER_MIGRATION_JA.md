# 予測の worker 移設と既存端末の移行

## 移設前の棚卸し（main ae9483a）

- 計算は dashboard の `chartForecast.ts`。`PriceChartModel` と共有カードが表示時に計算し、`useForecastSuite` も記録用に計算していた。
- `useForecastSuite` の effect が新しい5分足の origin を `forecastLog.ts` の関数で記録。`suiba.forecastLog.v1`（SUI）／その末尾に `:WAL_USDC` を付けたキーへ localStorage 保存。直近288件で、同じ origin は追記しない。
- 同 hook が実績足に対して採点・答え合わせ・タッチ判定を実行。閉じている間の予測は存在せず、採点・校正も停止。端末ごとに履歴が別だった。
- `forecastCalib.ts` が幅だけを学ぶ。状態は `suiba.forecastCalib.v1`（SUI）／`:WAL_USDC`。30件から評価、以後10件刻み。80%目標・±3pt不感帯・誤差半分の歩幅・[0.7,1.5] clamp・0.01丸め。
- 変更があったとき hook が `Date.now()`、件数、収まり率、倍率、拡縮方向から CalibEvent を生成。`stageCalibration` が件数で重複を抑制し、30分以内の変更だけ `calibText` により［学習］を生成。実況そのものも端末ローカル。

## 移設後

計算・採点・校正の関数を shared へ移動し、従来の import は互換 re-export にする。計算式の変更はない。`BotEngine.tick()` の足取得・検証後に worker エンジンを呼ぶ。売買開始の有無や dashboard の接続有無によらず既存取得サイクルで進む。予測失敗は表示用の `forecastError` に記録し、戦略・注文・安全停止判定へ渡さない。GET は保存処理を起動しない。

API の既存 snapshot/summary に、コーン（300/900/3600秒）、288件の採点窓、収まり率、校正状態、最新の答え合わせ、校正イベントを載せる。ブラウザは新しい予測を作らず、localStorage への予測・校正書き込みもしない。共有カードも worker のコーンを使う。

bot.sqlite の `bot_runtime_state` の `forecast.v1:<pair>` が状態の正本。`forecast_records` は予測の保存履歴、`forecast_answers` はホライズン完了後の採点と方向判定、`forecast_calibrations` は ID・発火時刻・件数・収まり率・新旧倍率、`forecast_imports` は端末移行の原データと採否。状態とイベントはトランザクションで保存する。288件を越えた予測も履歴表から消さない。

［学習］は worker の保存イベントに同じ `calibText` を適用する。イベント ID を実況の ID とし、既読 ID を端末の実況状態へ保存（旧状態には default=[]）。端末を増やしても worker イベントは増えず、同じイベントは各端末で同じ ID となる。閉じていた間のイベントも次回接続で再生する。

## 移行手順と範囲

1. マージ・配置の前に、本番で現在有効な倍率を保持している端末を決める。この PR は配置しない。
2. 配置後、その端末から対象ペアに最初に接続する。ブラウザが認証・既存のペアヘッダーを伴う `POST /api/forecast/import` で保存済み記録と倍率を送る。最大600,000文字、型と倍率範囲を検証する。
3. 最初の非空データだけが倍率と scoredAt を採用する。×1.16 またはその後の実際の保存値をそのまま取り込む。固定倍率へのリセットはしない。worker が先に生成を開始していても、最初の実データの移行を受け付ける。
4. 同じ payload はペアを含む SHA-256 により冪等。応答を失っても再送できる。取り込みが失敗したら10秒後に再試行。元 localStorage を削除・更新しない。
5. 後続端末の記録は origin で統合し、同一 origin は既存の worker 正本を優先。採点窓は互換の直近288件。窓に入らないものや衝突した内容も raw payload と予測履歴表に保存する。後続の異なる倍率は `archived` として原状態を保存し、先に採用した倍率を上書きしない。最初の端末を誤った場合はこの履歴からの明示的な復旧が必要で、自動選択はしない。
6. 未接続端末、ブラウザの別 origin/profile、削除済み・壊れた・アクセス拒否された localStorage はサーバーから取得できない。元来存在しなかった閉鎖中の予測も復元しない。接続できる端末の有効な保存データだけが移行対象。過去の採点はその記録と保存済み実績足から同じ式で再計算する。旧実装にも独立した永続スコア累計は存在しない。

正本が端末間で一致することは API 読み取りと再起動復元テストで検証。現在の本番端末内の保存値はこの作業では読めていないため、本番移行の実施・実値の受領まで確認したとは主張しない。

## 互換性と稼働範囲

- 旧関数を ae9483a から取得し、import パスだけ調整して生成した固定 JSON フィクスチャで、上昇・下降・横ばい・板傾き・倍率境界の計算、記録、採点、校正を比較する。
- 現行の収まり率は途中までの足も数える。ホライズン終了前は採点ゼロにする等の変更はしない。最終結果は実際の次の足が存在してから保存する。
- 現行の288件窓と scoredAt の仕様により、件数が飽和した後は校正の新規バッチが進まない。予測の生成と各予測の最終結果保存は継続する。継続的なローリング再校正への変更は数式・校正規則の再設計になるため今回に含めない。
- 既存 worker は選択中のペアを取得する構造。状態はペア別に保存し、切替前の状態を保持する。同時に両ペアを取得する通信変更はしない。
- ブラウザを閉じても worker が稼働し足を取得できれば進む。worker 自身の停止・取得障害・メンテナンス中に予測を捏造しない。
- 24時間相当の足を供給する自動テストで、未接続の一巡とSQLiteの再起動復元を検証する。実時間24時間の本番運転は行っていない。
