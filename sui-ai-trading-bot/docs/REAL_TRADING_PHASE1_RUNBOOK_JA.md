# TradeCap Phase 1（testnet）実行手順書

本手順書は、設計書 `docs/REAL_TRADING_TRADECAP_DESIGN_20261025.md` の **§10 Phase 1（testnet で一巡）** を実行するための手順を定める。設計判断そのものは設計書側にあり、本書は「何を、どの順で、どう確認するか」だけを扱う。

- 前提：REAL の実装（設計書 §5・§6）が完了し、テストとビルドが通っていること。本書は未実装の機能の手順は書かない。
- 完了条件：設計書 §10 の受け入れ 1〜10 を全て通し、**証跡（digest 一覧）が揃うこと**。あわせて本書 §5 の較正データ採取までを Phase 1 の仕事とする。
- testnet の資産（SUI／DBUSDC／DEEP）に金銭的価値はない。ただし**手順は本番（Phase 2・mainnet）と同一に踏む**。testnet で手を抜いた手順は、そのまま本番の事故手順になる。
- プールは testnet `SUI_DBUSDC`（設計書 §2.3）。testnet にネイティブ USDC はない。

## 1. 事前準備チェックリスト

- [ ] **Bot 鍵の生成**：オーナーがウォレットアプリ等で Bot 用の鍵ペアを生成する（設計書 §5.2）。Worker が鍵を生成・表示する経路は使わない。
- [ ] **鍵の配置**：秘密鍵は Worker の環境変数 `SUIBA_BOT_PRIVATE_KEY`（`suiprivkey1…` 形式）だけに置く。次を満たすこと：
  - ログ・DB・スナップショット・運用 API・例外メッセージに鍵（およびその断片）を含めない。起動時検証のログは Bot アドレスのみ出す。
  - `.env` ファイルを使う場合は権限 600 とし、リポジトリに含めない（`.gitignore` に入っていることを確認する）。
- [ ] **2 アドレスの確定**：オーナーアドレス（ウォレット）と Bot アドレス（上記鍵から導出）を確定し、取り違えがないよう両方を記録する。資金を持つのはオーナー側だけであり、Bot アドレスは TradeCap とガス用 SUI だけを持つ（設計書 §9.1）。
- [ ] **DeepBook SDK の版固定**：Worker へ追加する `@mysten/deepbook-v3` のバージョンを実装と同時に固定し、pnpm-lock に記録する（設計書 §5.5）。
- [ ] **REAL 設定の置き場所**：REAL 設定画面の場所（設計書 §11 #4）が未決の場合は、Phase 1 の着手前に決める。本書の手順は置き場所に依存しない。

## 2. 資産の入手

入手経路は公式 docs（Fees and Funding）の案内に従う。testnet DEEP には faucet がない（設計上、誰も DEEP やテストコインを mint できない）ため、DEEP と DBUSDC の入手は token request form が本命になる。

### 2.1 testnet SUI（faucet）

- [ ] オーナーアドレスへ faucet で testnet SUI を請求する（ブラウザ／Discord／cURL の経路がある）。
- [ ] Bot アドレスへも faucet で testnet SUI を請求する。Bot の SUI は**ガス専用**であり、BM には入れない（設計書 §2.4）。
- [ ] faucet にはアドレス・IP ごとのレート制限があるため、請求は残高が実際に減ったときだけ行う。
- [ ] ガス用に、各アドレスとも少なくとも 1 SUI を手元残高として保持する（公式ガイドの目安）。

### 2.2 DBUSDC と DEEP（token request form）

- [ ] **DeepBook Testnet token request form** から DEEP と DBUSDC（等の quote 資産）を請求し、オーナーアドレスで受け取る。これが DEEP と quote 資産を直接付与する確実な経路である。
- [ ] 代替経路（当てにしない）：ホワイトリストの testnet DEEP_SUI プールで faucet SUI を DEEP に swap できる（BalanceManager 不要・手数料ゼロ）が、板が薄く断続的なため、本命の到着を待てない場合の補助に限る。
- [ ] 用途の切り分け：DBUSDC は取引資金として BM へ入れる分。DEEP は手数料フロート用（§5.4.2）に BM へ入れる分であり、取引資金と混ぜて考えない。BM 外に DEEP を置いても手数料は払えない。

### 2.3 入手後の確認

- [ ] オーナーアドレスの残高（SUI／DBUSDC／DEEP）と Bot アドレスの残高（SUI）をそれぞれ確認し、金額を記録する。
- [ ] Bot アドレスに SUI 以外の資産が入っていないことを確認する（入っていたら設計書 §9.1 の構成から外れている）。

## 3. オーナー側セットアップ

設計書 §4.1（初期セットアップ）を実行手順に落としたもの。すべてオーナー署名の操作であり、Worker は代行しない。

1. [ ] **ウォレット接続**：ダッシュボードでオーナーウォレットを接続する。
2. [ ] **BalanceManager 作成**：`createAndShareBalanceManager` をオーナー署名で実行し、生成された **BM オブジェクト ID を記録**する。
3. [ ] **入金**：取引資金（DBUSDC、必要なら SUI）と手数料用 DEEP を BM へ `deposit` する。DEEP の量は §5.4.2 の定義（最大注文手数料の回数分）で考え、Phase 1 では較正データ採取（本書 §5）に足る量を入れる。
4. [ ] **TradeCap 発行と Bot への移転**：`mint_trade_cap` で Cap を発行し、Bot アドレスへ移転する。tx の構成は **1 tx（同一 PTB で発行＋移転）** と決定済み（設計書 §11 #5、2026-11-10）。**TradeCap のオブジェクト ID を記録**する。
5. [ ] **REAL 設定への登録**：BM ID・TradeCap ID・オーナーアドレス・Bot アドレスを REAL 設定（設計書 §5.3）に登録する。`network=testnet`、`poolKey=SUI_DBUSDC`、`payWithDeep=true`（2026-11-10 決定）とし、上限（`maxOrderUsdc`／`dailyRealLimitUsdc`）はテスト用に極小に置く。`enabled` はまだ true にしない。
6. [ ] **Worker 起動時検証の通過確認**：Worker を起動し、次がすべて通ることを確認する（1 つでも崩れていたら REAL は有効化されない＝フェイルクローズが正しい挙動）：
   - BM の `owner` が登録済みオーナーアドレスと一致する
   - TradeCap が Bot アドレスに存在し、その Cap が当該 BM のものである
   - Cap が失効していない
7. [ ] **有効化**：検証が通った状態で、REAL 設定の `enabled` を専用操作（確認ステップ付き、設計書 §5.3／§8.3）で true にする。

## 4. 受け入れ試験チェックリスト

設計書 §10 のチェックリスト 1〜10 をそのまま引く。各項目で「実施すること」を行い、「残す証跡」を記録する。**digest 一覧が Phase 1 の完了証跡そのもの**であり、項目ごとに欠かさず残す。

- [ ] **1. ダッシュボードでウォレット接続 → BM 作成 → テスト資産を入金**
  - 実施すること：本書 §3 の 1〜3 を行う。
  - 残す証跡：BM 作成 tx の digest、入金 tx の digest（資産ごと）、BM ID。
- [ ] **2. TradeCap 発行 → Bot アドレスへ移転 → Worker 側の起動時検証（§4.1-5）が通る**
  - 実施すること：本書 §3 の 4〜6 を行う。
  - 残す証跡：発行・移転 tx の digest（§11 #5 の構成どおり）、TradeCap ID、起動時検証が通った Worker ログ（Bot アドレスのみを含むもの）。
- [ ] **3. REAL 設定（network=testnet、executionSource=TRADECAP、上限はテスト用に極小）で Worker 起動**
  - 実施すること：本書 §3 の 7 を行い、REAL 有効な状態で Worker が稼働し続けることを確認する。
  - 残す証跡：有効化の操作記録、稼働開始時刻、上限値の設定内容。
- [ ] **4. 戦略シグナルまたは手動相当の経路で発注 → 約定確認 → `real_trades` に digest 付きで記録される**
  - 実施すること：買い・売りの往復を少なくとも 1 回ずつ通す。約定数量・約定価格は OrderFilled 系イベントと BM 残高差分の双方で突き合わせる（設計書 §6.3）。
  - 残す証跡：発注・約定 tx の digest、`real_trades` の該当レコード（内部注文 id と digest の対応）。
- [ ] **5. 指値（未約定）を出してキャンセルが効くこと。一括キャンセルも確認**
  - 実施すること：約定しない価格の指値を出し、個別キャンセル（`cancelOrder`）と一括キャンセル（`cancelAllOrders`）の両方を確認する（設計書 §6.6）。
  - 残す証跡：配置・個別キャンセル・一括キャンセルの各 tx digest、onchain order_id。
- [ ] **6. 緊急停止：新規停止＋未約定一括キャンセルが連動すること**
  - 実施すること：未約定注文がある状態で緊急停止を発動し、新規発注が止まることと一括キャンセルが発行されることを確認する（設計書 §7.2）。解除は手動のみであり、解除しても REAL が自動で再有効化されないことも確認する。
  - 残す証跡：一括キャンセルの tx digest、監査記録と運用画面の表示内容（対象件数・成功可否）。
- [ ] **7. 照合：Worker を送信直後に落とす等の異常系で、再起動後に §6.5 の照合で状態が復元される（または HALTED で止まる）こと**
  - 実施すること：発注 tx の送信直後に Worker を落とし、再起動後の照合（digest 記録済みなら確定状態の取得、digest 不明なら未約定一覧と BM 残高の突き合わせ、設計書 §6.5）で状態が復元されるか、説明できない差分で HALTED になるかを確認する。
  - 残す証跡：対象 tx の digest（記録されていた場合）、照合結果の記録、HALTED になった場合はその事象表示。
- [ ] **8. 失効ランブック：`revoke_trade_cap` 後に Bot の発注が失敗すること、出金で全額戻ること**
  - 実施すること：本書 §6 の戻し手順を実際に踏む。失効後に Bot の発注が失敗することまで確認する。
  - 残す証跡：失効 tx の digest、失効後の発注失敗の記録、未約定キャンセルと全額出金の tx digest、出金後の BM 残高（0 であること）。
- [ ] **9. ガス枯渇：Bot の SUI を抜いた状態で発注停止＋表示が出ること**
  - 実施すること：Bot アドレスの SUI を閾値（`minBotGasSui`）未満まで抜き、REAL 発注が停止して運用画面に表示されることを確認する（設計書 §7.4）。確認後は SUI を戻す（オーナーの通常送金、設計書 §4.2）。
  - 残す証跡：発注停止の記録と運用画面の表示内容、送金 tx の digest。
- [ ] **10. PAPER 回帰：モードを PAPER に戻し、従来の検証（テスト全件＋PAPER サイクル）が無傷であること**
  - 実施すること：REAL を無効化してモードを PAPER に戻し、リポジトリの従来の検証（typecheck・lint・全テスト・ビルド）と PAPER サイクルが無傷であることを確認する。
  - 残す証跡：検証コマンドの結果（件数・成否）、PAPER サイクルの実行記録。

## 5. 較正データの採取

Phase 1 は受け入れ試験の通過だけでなく、**§5.4 の初期値を実測で置き換えるまでが仕事**である。次を副産物として必須で採取し、結果を設計書 §5.4 の各初期値に反映する（反映は別途 PR で行う）。

- [ ] **poolTradeParams の実値**：testnet `SUI_DBUSDC` の takerFee／makerFee／stakeRequired を `poolTradeParams` で読み、記録する（§5.4.1 のキャッシュ実装が読む値そのもの）。
- [ ] **tx ごとの gasUsed サンプル**：Phase 1 で発生した全 tx の effects.gasUsed（MIST）を集める。§5.4.3 の中央値（直近 20 件）の前提と sanity 上限（初期値 0.5 USDC）の妥当性、およびコールドスタート要件（5 件）の較正材料にする。
- [ ] **手数料の実績と見積もりの差**：約定ごとに、実績手数料（資産と額）と ProfitGuard の見積もり（taker レート前提）を並べて記録し、乖離の方向と大きさを見る。
- [ ] **注文種別の比較**：成行相当（`placeMarketOrder`）と価格上限付き IOC 指値の双方で、約定率とスリッページ（板の mid／直近約定からの乖離）を記録する。設計書 §11 #3（注文種別の決定）の判断材料にする（§6.2）。
- [ ] **DEEP フロートの消費ペース**：注文回数に対する DEEP 残高の減り方を記録し、§5.4.2 の回数しきい値（目標 1,000 回分／警告 200 回分／停止 50 回分）の較正材料にする。

## 6. 異常時の戻し方

異常時（Worker の想定外挙動、鍵漏洩の疑い等）は設計書 §7.5（失効・資金退避ランブック）の順で止める。**失効とキャンセルは Worker が死んでいても実行できる**：

1. ウォレット（またはダッシュボード）から `revoke_trade_cap` を実行し、Bot の売買権限を剥がす。
2. BM の未約定注文をオーナー権限でキャンセルする（オーナーは proof を自分で生成できる）。
3. BM から全額をウォレットへ出金する。
4. Bot アドレスの鍵が漏れた疑いがある場合は、その鍵を廃棄し、新アドレス＋新 Cap で再構成する（旧アドレスの SUI 残高は回収可能なら移す）。

あわせて REAL の切り離しとして：

- REAL 設定の `enabled` を false に戻し、モードを PAPER に戻す（受け入れ #10 の PAPER 回帰と接続する）。PAPER 側は REAL の状態に依存せず従来どおり動くことが設計の前提である。

## 7. 完了判定と Phase 2 への申し送り

- **完了判定**：§4 の受け入れ 1〜10 が全てチェック済みで、各項目の証跡（digest 一覧）が揃い、§5 の較正データが採取できていること。この 3 点が揃った時点で Phase 1 は完了とする。
- **Phase 2 への申し送り**：設計書 §11 #1（Phase 2 の投入額と、REAL の 1 回上限・日次上限・スキーマのハードキャップ値）の判断材料として、次をサマリとして残す：
  - ガス実績（tx 種別ごとの gasUsed の分布と中央値）
  - 手数料実績（poolTradeParams の実値、実績手数料と見積もりの乖離）
  - 約定率とスリッページ（注文種別ごとの比較、§11 #3 の判断材料を兼ねる）
  - DEEP フロートの消費ペース（Phase 2 で BM に常備する DEEP 量の目安）
- Phase 2 ではプールが `SUI_USDC` に変わり、BM と Cap は mainnet で新規に作り直す（testnet の BM・Cap は流用できない、設計書 §10）。本書の §2〜§4 の手順は、資産入手の経路（faucet／form が使えないこと）を除き mainnet でも同じ順で踏む。
