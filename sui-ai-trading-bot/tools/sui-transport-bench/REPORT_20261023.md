# Sui通信比較：承認済み小規模preflightの結果

実施日: 2026-10-23。結論: Nativeの2回目が10秒期限に達し、停止条件に従って打ち切った。
方式の優劣を判断する標本数ではなく、本番方式の切替根拠は得られていない。

## 実行条件と隔離

- 接続先: `https://fullnode.mainnet.sui.io:443`。両方式ともSUI metadataのみ。
- SDK 2.37.0、protobuf-ts grpc-transport 2.11.1、grpc-js 1.14.6。専用package-lockで固定。
- Windows x64、Node 24.14.0、同梱Undici 7.21.0。Bot指定Node 24.22.1と異なる。
- 個別子プロセス、逐次要求、完了後5秒以上の間隔、論理要求10秒期限。
- WebはSDK標準text形式、NativeはTLS、grpc-js retry無効。アプリretryなし。
- Botのworker、DB、scheduler、Docker、LIVE/PAPER/24時間運用検証は起動・操作していない。
- Botのpackage.json、pnpm-lock.yaml、sui-client、sharedのtracked差分は実施後もゼロ。
- 実行時作業ブランチHEADは2a5fcfcf000109803578ce038560586f25b47b22。
  main調査基準0e076ec2とは別であり、この試験は独立ハーネスの検証。
  Bot本体のmain実行結果ではない。ハーネスのソースhashを証拠に保存した。

## 要求数と計測修正

初回13:18:46 UTC開始のWeb読み取りは成功（995.023ms）したが、
SDK構築後にカウンターを取り付けたため、保持済みメソッドを計測できず0回と記録。
その直後に停止した。この1要求は方式比較から除外するが、承認された負荷上限に算入する。
0という計測値は実通信ゼロを意味しない。

SDK生成前にカウンターを取り付け、バインド後も正しく計数するオフラインテストを追加した。
再開計画は29ペア58要求へ縮小。13:19:31 UTC開始の再開では3要求で停止した。
**総実行数は4論理要求（Web2、Native2）。追加試行や復旧確認通信は行っていない。**
再開分の各要求はtransport unary呼び出し1回を確認した。
これはRPC呼び出し数であり、パケットキャプチャによるwire再送回数の測定ではない。

CPU/メモリも優劣を判断できない。

## 期限切れの解釈と未確認事項

10秒期限でAbortSignalを発火し、処理終了を約10012msに観測した。
これはNodeタイマーと処理スケジューリングを含む経過時間であり、12msの追加予算を設定したものではない。
期限到達後は要求を再開せず子プロセスを終了した。

現在の証拠だけではDNS失敗、接続確立待ち、TLS、HTTP/2 channel再接続、応答待ちを区別できない。
Nativeの初回成功後に次の要求が失敗したことから、接続再利用の不具合とも断定できない。
復旧時間は未測定。接続ID/IP、詳細phase timing、ピークメモリも未測定。
BotのapiFetch全本文バッファリングや安全停止への統合はこのハーネスの対象外。

次に進める場合は、まずローカルfixtureで接続・応答phase観測とcancelの検証を追加し、
実通信に必要な追加観測と回数を別途提示する。追加のSui実通信、Docker、本番切替には別の事前承認が必要。
現在の本番通信方式は維持する。
