# DeepBook P0: 取得周期・鮮度監視・停止診断

基準: main `4fe341e`。既存Provider、再構築、RiskEngine、Profit Guard、PAPER Ledgerを再利用します。LIVE・署名・実注文・自動再開は追加しません。稼働中の3100/3101環境やDBを変更して適用する作業は行いません。

## 確認できた原因と限界

既存Workerは処理完了後に60秒待っていました。実行開始の保存時刻から、実際の周期が約66〜74秒に伸びていたことを確認しました。既存監視は最後に検証した確定5分足が360秒を超えると停止します。取得周期の位相がずれると、次の足を取得する前に鮮度上限を越える場合があります。

2026-10-21 21:41 JSTの停止周辺には通信エラーのログはなく、前後の分析記録は継続していました。ただし当時の停止スナップショットがないため、次の足がその瞬間すでに公開されていたか、処理のどの段階だったかまでは確定していません。既存の停止が誤りだったと断定して鮮度制限を緩める変更はしていません。

## 取得スケジュール

- 周期待機・所要時間は `performance.now()` の単調時計で管理します。UTCの時計は初期位相と設定変更時の位相合わせ、および記録用の時刻に使います。処理完了時刻を次の周期の起点にはしません。
- 標準60秒周期のDeepBookは、5分足確定後10秒を含む固定グリッドで取得します。通常は毎分10秒の位相です。10秒はProviderの応答保証ではなく、検証用の取得予算です。
- 最初の起動時は即時に1周期実行します。位相合わせ時も開始間隔30秒未満にはしません。このため初期の1〜2周期は固定位相からずれる場合があります。
- 正常に返った足がちょうど1本前で、境界後の既存60秒の許容窓内なら、その境界につき最大1回だけ再確認します。標準の再確認目標は境界後40秒、最小開始間隔は30秒です。通信失敗やAPIバックオフを追加ポーリングで迂回しません。
- 同時実行は1周期のみ。処理が長引いて過ぎたスロットは飛ばし、追いつき実行を連打しません。開始間隔は最低30秒で、起動・反映待ちを含めても最大2周期/分です。HTTPの集約・短期キャッシュ・API単位の直列化・429制御は維持します。
- GeckoTerminalの標準設定は変更せず、境界再確認はDeepBookを使用する場合だけ行います。GeckoTerminalも周期の累積ずれは防止します。
- 既存の `intervalMs` を維持します。非常に長い設定周期では360秒の鮮度を維持できず、引き続き安全停止します。24時間検証では標準60秒を使用してください。

## 独立した時刻と状態

SQLiteの既存 `operation_state` に、後方互換の追加フィールドとして保存します。既存履歴を削除する移行はありません。

| フィールド               | 意味                                                                             |
| ------------------------ | -------------------------------------------------------------------------------- |
| `lastFetchAttemptAt`     | 市場データ一式の取得試行開始                                                     |
| `lastFetchSuccessAt`     | Providerから取得一式が返った時刻                                                 |
| `lastTransportSuccessAt` | 市場データAPIでHTTP本文の受信が成功した時刻                                      |
| `lastMarketAt`           | 取引用ローソク足の検証成功時刻（既存）                                           |
| `lastMarketClosedAt`     | 最終確定5分足の終了時刻（既存）                                                  |
| `lastAnalysisAt`         | 分析結果の保存成功時刻                                                           |
| `fetchStartedAt`         | 現在の市場データ取得開始。取得終了時とWorker再起動時に解除                       |
| `lastFetchDurationMs`    | 前回取得の単調時計による所要時間                                                 |
| `nextFetchAt`            | 次回取得予定。取得が終わらなければ重複起動しないため、実行を保証する時刻ではない |

画面では通信の直近成功と、確定足の「鮮度内／更新待ち／期限切れ／未取得」を分けて表示します。HTTP成功や取得中であることは、古い足を許可する根拠にしません。これらの時刻は24時間計測のsample/cycleにも保存し、JSON/Markdownレポートに含めます。

## 維持する安全条件

確定足の鮮度上限は **360秒のまま**、取得成功のない期間の上限も **360秒のまま**です。古い足は取得中でも停止します。約定直前の `validateCandles`、見積もり期限、板10秒、スプレッド・流動性、RiskEngine、Profit Guardの再確認も維持します。

取得一式には単調時計で45秒の上限を追加しました。取得が終わらなくても監視タイマーで停止し、遅れて成功が返ってもその周期から約定しません。期限超過した取得が残っている間の手動開始も拒否します。I/O待ちの間も通常停止・緊急停止のAPIは処理できます。取得終了やAPI回復だけでは停止フラグを解除しません。

「取得成功から67秒、確定足から361秒」は停止対象のままです。この状態を取得中だから許可するのではなく、正常な反映待ちでは事前の境界取得・限定再確認で新しい足を得る設計です。Providerが期限内に正しい足を返さなければ、引き続き停止します。

## APIと停止の診断

DeepBookの既存パスをallowlistで識別します。追加のAPIは導入していません。

| 処理               | 識別名                       |
| ------------------ | ---------------------------- |
| OHLCV              | `OHLCV_FETCH` と `timeframe` |
| 注文板             | `ORDERBOOK_FETCH`            |
| Indexer状態        | `MARKET_STATUS`              |
| プール確認         | `PROVIDER_HEALTH`            |
| 再構築の無約定証拠 | `TRADE_EVIDENCE_FETCH`       |

失敗時の `UPSTREAM_REQUEST_FAILED` には開始・終了時刻、単調時計による所要時間、タイムアウト段階、HTTPステータス、再試行回数、同じ処理の最終成功時刻（現在のプロセスで観測した値）を記録します。接続とヘッダー待ちの区別を実際には得られない場合は `HEADERS_OR_CONNECT` とし、接続タイムアウトと推測しません。URLはredacted、時間足はallowlist値のみで、キー・ヘッダー・本文・生の例外メッセージは出力しません。

SQLite `operation_events` には `kind=API` の監査レコードを追加します。API異常の即時停止を先に実行し、その後に監査を保存する順序です。保存に失敗した場合も取引を進めません。

`MARKET_DATA_STALLED` 時には既存監査ログの `details` とコンソールへ以下を記録します。

- 判定時刻、確定足の経過秒数、取得成功からの経過秒数、検証成功からの経過秒数
- 取得中か、現在の取得開始時刻・経過時間、前回所要時間、次回予定時刻
- 詳細理由: `CANDLE_STALE` / `FETCH_DEADLINE_EXCEEDED` / `FETCH_SUCCESS_STALE` / `NO_VALID_MARKET_DATA`

## Windows 11: 既存検証と分離した再テスト

この変更を含むチェックアウトで実行します。既存3101環境のログ・履歴は保持します。ヘルパーの `--profile=p0` をすべてのコマンドに付けると、`suiba-deepbook-p0`、ポート3102、新規env/secret、新規ボリュームを使います。

```powershell
Set-Location D:\Source\SuiBa\sui-ai-trading-bot
node docker/deepbook-24h.mjs init --profile=p0
node docker/deepbook-24h.mjs up --profile=p0
```

`docker/.env.deepbook-p0` はGit対象外です。ポート競合時だけ `VALIDATION_PORT` を別の空きポートへ変更します。本番や既存検証のenvをコピーしないでください。

1. `http://127.0.0.1:3102` を開きます。
2. `docker/secrets/deepbook-p0-admin.txt` をエディターで開き、専用トークンを接続欄へ貼り付けます。トークンをログ・チャットに貼らないでください。
3. DeepBookの正常取得、未解決欠損0、Profit Guard有効、60秒周期を確認します。初回の証拠取得中は待ち、異常があれば理由を確認してください。
4. Bot停止状態で24時間計測を明示的に開始します。続いて30秒を目安に画面からPAPER運用を手動開始します。

```powershell
node docker/deepbook-24h.mjs begin --profile=p0
node docker/deepbook-24h.mjs status --profile=p0
node docker/deepbook-24h.mjs report --profile=p0
node docker/deepbook-24h.mjs logs --profile=p0
```

`docker/artifacts/deepbook-p0.json` と `.md` が新しいレポートです。24時間未満や記録不足は合格になりません。今回の修正作業で実際の24時間試験を完了したとは扱いません。

停止・再起動・バックアップも専用環境だけを対象にします。再起動後もBotは停止したまま、開始には手動操作が必要です。

```powershell
node docker/deepbook-24h.mjs stop --profile=p0
node docker/deepbook-24h.mjs restart --profile=p0
node docker/deepbook-24h.mjs backup --profile=p0
```

ボリューム削除や既存DBの初期化はしません。`backup` はP0コンテナだけを停止し、WAL/SHMを含むDBディレクトリとレポートを新規フォルダーへ保存し、停止したままにします。
