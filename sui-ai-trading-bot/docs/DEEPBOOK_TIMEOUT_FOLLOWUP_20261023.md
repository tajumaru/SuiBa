# DeepBook本文タイムアウト・安全停止の追加調査

調査日: 2026年10月23日（日本時間）。原因調査のみ。ソースコード、設定、Botの稼働状態は変更していない。

## 結論

稼働中の検証コンテナのSQLiteを読み取り専用で調査し、画面のDeepBook一式取得 **36,182ms** と完全一致する周期を特定した。失敗した通信はDeepBook Indexerの `GET /ohclv/SUI_USDC?interval=5m&limit=1000`。初回は本文、再試行1回目はTLS、2回目はTCP接続段階で期限に達した。

最初の通信失敗でPAPER Botを停止し、再試行や後続周期が成功しても停止を解除しない現行設計が、異常停止を維持する直接の理由である。外部遅延の発生源がサーバー、回線、Windows、Dockerのどこかは未確定。

「999本・再構築2本・未解決0本」は前周期の品質情報が残ったもの。今回の5分足取得は品質更新前に失敗した。停止理由は初回BODY timeoutを保持し、周期最終エラーはCONNECT timeoutとなる。該当周期に `MARKET_DATA_STALLED` はなく、45秒取得監視による停止ではない。

## 実装・設定

- `packages/shared/src/http-errors.ts` の `classifyHttpFailure`: 本文段階の期限切れを分類。
- `packages/shared/src/api.ts` の `ApiAccess.run`: API別直列化、同一要求集約、再試行。再試行前に停止コールバックを呼ぶ。
- `apps/worker/src/engine.ts`: `onTransientFailure` で初回停止。`tick` の最終失敗でも安全停止。
- `packages/market-data/src/deepbook.ts`: 1試行8秒、追加再試行2回。5分・15分・1時間足、再構築の1分足ページを逐次取得。
- `packages/market-data/src/deepbook-transport.ts`: HTTP/2再利用、失敗時の接続破棄、GOAWAY対応、アイドル120秒。再試行時も新規接続で失敗しており、再利用接続だけを原因にできない。
- `packages/sui-client/src/index.ts`: SuiGrpcClientによる別経路。共通層10秒、一時障害の追加再試行0回、healthは120秒再利用。今回特定した要求はgRPCではない。
- 再試行待機は1〜1.25秒、2〜2.5秒。429は別途Retry-Afterを処理し、最大2回追加、60秒を超える指定はクールダウンを保持して自動再試行を断念する。
- `apps/worker/src/operations.ts`: 一式取得45秒、確定足・検証済み市場データ360秒、監視15秒。連続エラー3回の監視もあるが、初回停止を猶予する条件ではない。
- `apps/worker/src/index.ts`: RESETとSTARTは別操作。起動時も停止。MODEはPAPER限定でLIVEは未対応。

## 優先度と推奨対策

| 優先度 | 対策・影響 |
|---|---|
| P0 | 通信異常中の新規注文禁止、緊急停止、台帳整合性、実行直前の鮮度・見積もり検証を維持する。 |
| P1 | PAPER限定で通信待機と解除必須の停止を区別。初回停止コールバックとtickの最終停止の両方を設計する。単純な再試行追加では停止維持は変わらない。 |
| P1 | 自動復旧は一時通信障害に限定し、複数周期の正常、全時間足・板・Indexer・gRPC・台帳、バックオフ終了を確認する。手動停止・緊急停止・台帳異常は対象外。 |
| P1 | 1試行8秒、再試行、一式45秒、板10秒鮮度の時間予算を整合させる。板更新を注文判断に近づける。 |
| P1 | 過去の停止理由、今回の最終エラー、現在の通信状態、品質取得時刻を区別して表示する。 |
| P2 | 実測分布に基づく期限調整、限定並列化、再構築結果の再利用。無条件の延長・並列化は停止検知遅延や429を増やす。 |
| P2 | 代替接続先を検証。DeepBookの代替は市場・データ仕様・証拠・鮮度が同等か確認し、別市場への切替で安全条件を迂回しない。 |

コード変更前のPAPER運用では、停止したまま収集を続け、複数周期の正常と全検証を確認してから手動解除・開始を判断する。解除の反復は対策にならない。Dockerのhealthyは市場正常・Bot稼働の保証ではない。
