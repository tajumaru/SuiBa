# TradeCap Phase 1 残り手順のコード総点検（2026-11-20）

対象コード：PC Bot が実際に動かしている版（main 7f87bf4、PR #344 まで）。
物差し：手順書 §4（受け入れ 4・7・8）、設計書 §6.5／§7.5／§11.9（2026-11-18 決定）。
方法：REAL 経路の全ファイル（worker/src/real/ 12本＋scripts/real-*.ts 5本＋engine/http-routes の接続部）を読み、関連テスト8ファイル70件を実行して全緑を確認。

## 結論

残り手順（初約定 → S3 → S4 → kill switch → 証跡）は、コードの裏付けがある。止める・再開する・失効させるの3つとも、設計どおりの作りになっている。想定と違う点が1件だけあり、現場での扱いを下に決めた（発見1）。Phase 1 の進行を止める問題ではない。

## S3：ポジション保有中の停止 → 再開

- 再開ゲート（real-resume.ts）に「保有ゼロ」の条件はない。必要なのは、保有が台帳と開始残高で**説明できる**こと（§11.9.2-6 のとおり）。
- ゲートは12項目（取引の後片付け／履歴の取得／台帳の照合／残高の説明／未約定ゼロ／本人確認／TradeCap／ガス／DEEP／リスク／ProfitGuard／相場）。リスクと ProfitGuard は Bot 本体が毎サイクル記録した判定（2分以内）を読み、NOT_EVALUATED は遮断しない（2026-11-18 の本人決定どおり）。
- 停止は画面の stop／emergency が REAL 専用ラッチに直結（http-routes.ts → engine.acceptExecutionStop → database.acceptStop：世代+1・承認クリア）。再起動してもラッチはDBに残り、ゲートを開けない限り署名しない（real_control の初期値は halted=1）。

## S4：送信中の停止

- 発注は1本の直列キュー（execution.ts）。順序は「世代を記録 → 署名可否チェック → tx 構築 → **送信前に digest 等を耐久記録** → 再チェック → 署名 → 再チェック → 送信」。
- 途中で停止が受理されると世代が進み、署名直前の再チェックで REAL_SIGNING_HALTED となり**送信されない**。記録だけ残った tx は「送られた可能性あり」として照合対象に残る（消えない）。
- 送信後に結果が不明な場合は UNKNOWN のまま保持し、次の発注は照合が終わるまで自動で拒否（REAL_RECONCILIATION_PENDING）。推測で失敗扱いにしない（§6.5）。
- この一連は単体テストで担保済み（世代フェンス、永続化失敗時に署名しない、UNKNOWN の不変、OOM 後再走査で二重計上しない、取消と競合約定の別キー管理、BM 不一致の隔離ラッチ）。現場でタイミングが合わず再現できなくても「テスト担保あり」と記録してよい（手順書 §4-7 の読み替え）。

## kill switch：失効 → 取消 → 出金

- オーナーツール（real-owner-cli.ts）に3コマンドが揃っている：`revoke-trade-cap` → `cancel-all` → `withdraw-all`。Worker が死んでいても、オーナー鍵だけで実行できる（§7.5 の順序どおり）。
- 失効は取り消し不可。その Cap では二度と売買できない。だから kill switch は最後（Phase 1 の締め）に置く現行計画が正しい。
- 失効後の Bot の発注はチェーン側で失敗する（TradeCap の proof 検証で弾かれる）。受け入れ §4-8 の「失効後に Bot の発注が失敗すること」はこの形で確認する。

## 発見1（主）：残高の「説明」は、約定のたびに開始残高の刻み直しが要る

- 設計では、約定イベントが残高の増減（available／locked／settled の内訳）を台帳へ運び、再開時に「台帳で説明できるか」を自動判定する想定（§6.5-4、§11.9.2-5）。
- 実装では、その増減データを作る本番経路が**存在しない**（履歴ソース history-source.ts は注文イベントに数量だけを持ち、増減を持たない。増減を使うのはテストの fixture だけ）。台帳に自動で積まれるのは Bot 自身のガス支出のみ。
- 結果として、約定が1回でもあると再開判定の「残高の説明」は必ず差分あり（NG）になる。ゲートを開けるには、承認フローで差分を確認して開始残高を刻み直す（real-resume.ts の approve 経路：差分を先に表示・記録してから刻み直す）必要がある。これは2026-11-18 の本人決定（開始残高方式＋差分が出たら再承認で刻み直す）と一致する動きで、S1／S2 が通ったのもこの経路。
- **現場ルール**：刻み直す前に、表示された差分が約定内容と一致するか必ず目視で照合する（SUI の増分 ≒ 約定数量、DBUSDC の減分 ≒ 数量×価格＋手数料、DEEP の減分 ≒ 手数料）。一致しない差分があれば刻み直さず、HALTED として止める。
- Phase 2 への宿題：履歴イベントに残高増減を持たせる（indexer 注文イベント＋effects 解釈）か、設計側を現行方式に合わせて改訂する。mainnet では毎回の目視刻み直しは負担とリスクが大きい。

## 発見2（副）：失効しても Bot 側の「許可証チェック」は緑のまま

- 再開ゲートの TradeCap 検査（cap-valid.ts）は「Cap が存在し、Bot の所有で、正しい BM を指しているか」だけを見る。失効（BM 側の許可リストから外す操作）はこの3点を変えないので、失効後もゲート上は capValid=true になり得る。
- 実害の形：失効後にゲートを開けて合図が出ると、発注を試みてチェーンで失敗し続ける（自動で止める仕組みはない。1回ごとに少量のガスを消費）。Phase 1 では「失効後に発注が失敗する」こと自体が受け入れ確認なので許容。ただし失効後に再開承認を押す運用はしないこと。
- Phase 2 候補：許可リスト所属まで含めた Cap 検査、またはチェーン拒否が続いたら自動ラッチ。

## 現場チェックリスト（初約定が来たら）

1. **初約定の確認**：BM 残高の変化（SUI 増／DBUSDC 減）と indexer の約定イベントを突合。digest を証跡 manifest（data/real-phase1-evidence.json）の orderPlaced／orderFilled へ。
2. **S3**：ポジション保有のまま画面で停止 → Worker 再起動 → real-resume のドライラン。
   - 期待：未約定ゼロ・履歴・台帳はOK、「残高の説明」だけ差分あり（＝ポジション分）。
   - 差分が約定内容と一致するのを確認してから `--approve --reason=...` で刻み直し＋ゲート開放。
   - 一致しなければ開けずに報告（HALTED 相当）。
3. **S4**：次の合図の送信タイミングに合わせて停止を試みる。合わなければ無理に狙わず、「単体テスト担保あり（世代フェンス）」と記録して stopResumeS4 の証跡はテスト結果で代替する旨を manifest にメモ。
4. **kill switch（最後）**：real-owner-cli で revoke-trade-cap → Bot が発注に失敗することを1回確認（画面の監査に失敗記録）→ cancel-all（未約定があれば）→ withdraw-all → BM 残高が全資産 0 を確認。各 digest を manifest の killSwitch* へ。
5. **証跡**：`pnpm real:evidence` を実行し、チェックリスト（stopResumeS1〜S4、killSwitchRevoked／Cancelled／Withdrawn を含む15項目）が「あり」で揃うことを確認。
