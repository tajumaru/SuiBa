# POTARIO PC運用（testnet Bot）

PC 上の testnet Bot の運用メモ。手順の正本はスクリプトとこの文書。
PC の Codex は作業前にこの文書を読むこと。世代ごとの状態（今どのフォルダか等）は
ここには書かない（`pnpm pc:status` が出す）。ここには手順の入口・読み方・経緯・
判断の前提だけを置く。

## コマンド（sui-ai-trading-bot フォルダで実行）
- 再開： `pnpm pc:resume -- --reason=<理由（空白なし）>`
  エラーの解除→エンジン開始→判定→扉を開ける→最終確認までを安全ゲートつきで実行する。
  差分が0でない、またはチェックが1つでも false なら、扉を開けずに理由を表示して止まる。
- 状態： `pnpm pc:status`
  読み取り専用。正しい数字だけを出す（稼働・注文許可・残高差分・設定）。

## 読み取りの正しい方法
- `GET http://localhost:3100/api/state` には `Authorization: Bearer <ADMIN_TOKEN>` が必須
  （.env の ADMIN_TOKEN。値は出力しない）。トークンなしの 401 は異常ではない。
- /api/state の portfolio は BalanceManager の残高ではない。残高の話はそちらで判断しない。
- **残高の正本は `pnpm real:resume`（--approve なし）の差分一覧。**
  全18項目（SUI/DBUSDC/DEEP × available/locked/settled/owed/fee/gas）がすべて 0 なら、
  開始時に刻んだ残高とチェーン上が一致している。
- 開始残高（genesis）： SUI 5 / DBUSDC 9.89 / DEEP 114。
- 設定の読み書きも /api/state 経由（GET /api/settings は存在しない）。
  保存は POST /api/settings に設定オブジェクト全体を送る。
- **「Bot が止まっている」という判定は、独立した2つの具体確認が一致したときだけ下す。**
  1回の応答なし・ポート確認の失敗だけでは死んだことにならない（2026-11-22 未明に
  1回の読み違いで「停止」と誤判定した。実際は稼働中だった）。
  確認の例：プロセスの有無、3100番への応答、data/ のファイル更新時刻。
  PC 側の道具（リモートの Codex 等）が応答するなら PC は起きているので、
  問題はプロセス側に絞る。画面のスクリーンショットは生死の証拠にならない
  （古い表示のことがある）。鮮度は状態の時刻で読む。

## 停止と再開の仕組み（スクリプトが守る前提）
- 画面/API の停止は「売買の停止」まで。プロセスは画面を出すため残り、3100番も使用中のまま。
- 停止は記録に残る。再起動しても自動では再開しない。
- 判定記録の鮮度は2分。扉（resume の approve）と稼働（control start）は別レイヤーで、
  扉が閉じている間はエンジンが回っても注文は出ない。
- プロセスを終わらせる必要があるときは、停止を確認してから taskkill し、
  3100番が空いてから data をコピーする。

| 停止の種類 | 復旧手順と順序 |
| --- | --- |
| 起動前から残っていたエラー | `pc:resume` を実行する。保存されていた停止の記録を照合して解除すると、読み取りが再開される。その後に開始と注文許可の確認を行う。 |
| 起動後に起きた外部読み取りの HTTP 500 | 停止中に同じ読み取りが成功し、通信の安全確認が済んだら、再起動せずに `pc:resume` を1回実行する。エラー解除 → 開始 → 残高などの確認 → 注文許可の順で進む。原因を確認できないエラーは解除されない。 |
| 通信の復旧確認待ち | 読み取りによる復旧確認が終わるまで待つ。すでに稼働に戻っていれば、`pc:status` で注文許可を確認する。停止中または注文許可が閉じていれば `pc:resume` を実行する。 |
| 緊急停止 | 原因を確認した上で、オーナーが専用の操作で緊急停止を解除する。エラーが残っている場合はその種類に応じて確認し、`pc:resume` を実行する。 |

## 注文だけが止まるとき（照合ペンディング）

- 症状： Bot は正常稼働の表示でエラーもないのに、買いシグナルが
  REAL_RECONCILIATION_PENDING で拒否され続ける。
- 仕組み： 送信記録（real_submission_intents）に結果不明（SUBMITTING／UNKNOWN）が
  1件でも残ると、安全のため全注文が止まる。60秒ごとの自動照合は
  読み取り専用モード（REAL_READONLY）でしか動かないため、取引モードでは
  結果不明が出ると、人が確認するまで詰まったままになる（現行の設計）。
- 切り分け： .env の REAL_DATABASE_PATH の SQLite を読み取り専用で開き、
  state が SUBMITTING／UNKNOWN の行を確認する。その digest がチェーンで
  どうなっているかは、Sui GraphQL の transaction(digest) { effects { status } } を
  設定済み URL と公開 URL（graphql.testnet.sui.io）の2経路で確認する。
- 解除： `pnpm real:resume`（--approve なし）を実行する。最初に照合が走り、
  チェーンで確認できた送信は確定する。その後、未確定が0件になったことと
  `pnpm pc:status` を確認する。扉がすでに開いているなら --approve は不要。
  **台帳を手で書き換えない。再起動もしない。**
- 注文のガス代は SUI.gas を開始残高より減らす。注文が約定しなくても
  ガス代の分だけ差分が出て、pc:status は「残高：差分あり」と表示し続ける。
  差分がガス代だけで説明できると目視確認できていれば、それ自体は異常ではない。
  開始残高の刻み直しは、次の停止・再開のときに差分を確認してから行う。

## コード更新の手順
- 旧世代フォルダは残し、新世代を新規 clone する。両世代は同時稼働させない。
- このスクリプトが入っているチェックアウトの `sui-ai-trading-bot` フォルダで実行する。

  ```powershell
  .\scripts\pc-generation-update.ps1 -From SuiBa17 -To SuiBa18 -SetEnv @{ REAL_ORDER_TYPE = "MARKET" }
  ```

- 対象は D ドライブの世代フォルダ。まず `-DryRun` で計画を確認できる。通常は開始前に
  確認を求め、`-Yes` で省略できる。`-SetEnv` は任意で、複数のキーを指定できる。
  `-Reason` には空白を入れず、文字・数字・ハイフン・アンダースコアを使う。
  省略すると、再開理由は「更新後の再開」になる。
- スクリプトは API で旧 Bot を停止し、`pc:status` で停止中・注文許可なしを確認する。
  旧プロセスの終了と 3100 番ポートの解放を確認してから `.env` と `data/` をコピーする。
  新世代では `.env` の指定キーを更新し、install と build の成功後に `pnpm dev` を
  新しいコンソールで起動する。画面の HTTP 200 を確認してから `pc:resume` と最後の
  `pc:status` に進む。
- 残高の説明だけで止まった場合は終了コード 2。表示された差分と約定内容をオーナーが
  目視で確認し、説明できる場合だけ新世代で表示どおり `real:resume --approve` を手動実行し、
  続けて `pc:resume` を実行する。残高差分の承認は手動のままとする。
  それ以外の失敗は終了コード 1 で、止まった段階を表示する。
- **更新後の想定状態**： 新世代は「停止中」で起動するのが正常（停止状態の引き継ぎ）。
  停止中は注文許可が「なし」になり、判定のチェック（取引の安全確認・利益の確認・
  相場の確認）も赤くなるが、異常ではない。pc:resume の1回目でエンジンが開始し、
  その後に残る問題は、既知の残高差分がある場合の「残高の説明」だけが想定どおり。
  それ以外の理由が残っていたら止まって報告する。

## 判断の前提（止まった後に人が決めること）
- 残高差分が約定内容と一致しないときは、開始残高の刻み直しをしてはいけない。
  まず差分と約定内容を目視で突き合わせる。
- 差分がすべて 0 でない再開は、理由が説明できる場合だけ進める。
