# AI 影運用（シャドーモード）設計書 ― 記録専用の AI 判断とルール戦略の答え合わせ

- 作成日：2026-11-11
- ステータス：S1/S2実装済み、OpenAI実アダプタは未有効化。本書はオーナーの「AIエージェントに取引を任せたい」表明と、進め方として影運用を選んだ決定（2026-11-11、`docs/DECISIONS_JA.md` 参照）に基づく
- 対象：`sui-ai-trading-bot`（Worker、SQLite、レビュー `docker/run-review.py`、公開 export `deploy/paper-check/export_snapshot.py`）

---

## 1. 目的・前提

### 1.1 目的

AI（LLM）に売買判断をさせる前に、その判断の質を証拠で測る。影運用では、AI の売買判断を**記録だけ**し、ルールベース戦略の判断と同一条件（同じサイクル・同じ入力）で並べて、既存レビューの物差しで答え合わせする。「AI がルールより上手いか」が数字で言えるようになってから、権限を広げるかどうかをオーナーが判断する。

影運用が生む副産物として、ルール側では貯まりにくい判断サンプル（買う／見送る＋根拠のラベル付き記録）が蓄積する。現行ルールは WAIT が大半で BUY 候補が少なく、学習・評価以前にデータが不足している（`docs/ML_DATA_AUDIT_JA_20261107.md` の段階基準が未達なのはこのため）。影の記録は、その不足を実弾のリスクなしに埋める。

### 1.2 非目的（やらないこと）

- AI の判断で注文を出す・止める・変えること（取引への関与は一切しない）
- ルール戦略のパラメータを AI の成績に合わせて自動調整すること
- AI の出力を安全停止・エピソード回復など安全系の入力にすること
- 本書の範囲で AI への権限移譲を決めること（卒業後の話は §10 の通り別途判断）

### 1.3 前提（不変条件）

1. **記録専用**。影モジュールは読み取りと追記だけを行い、注文経路・保有・設定には触れない。
2. **安全系に影響しない**。影の遅延・失敗・暴走があっても、tick の処理、エピソード制限（180秒/9回、板系は30分/61回）、429/500 の即停止といった既存の安全意味論は一切変わらない。
3. **同一条件の比較**。AI への入力は、そのサイクルでルールエンジンが見た情報の凍結スナップショット（§4）からのみ生成する。後から取得したデータ（後知恵）を混ぜない。
4. **卒業条件は事前登録**。閾値は運用を始める前に本書へ固定し、結果を見てから動かさない（既存レビューのフラグ規律と同じ）。
5. **数値の多くは仮置き**。cadence や閾値の確定値は §11 の未決事項であり、本書の数値は「仮置き」と明記したもの以外は既存コード・既存文書の実値である。

### 1.4 用語

| 用語 | 意味 |
|---|---|
| 影判断 | AI が記録専用に出す売買判断（BUY／WAIT）。注文には一切つながらない |
| スナップショット | そのサイクルでルールエンジンが見た入力の凍結コピー（§4） |
| トリガー | 影の呼び出しを行う条件（§6）。毎ティックは呼ばない |
| 卒業 | 事前登録した成績条件を満たし、「権限拡大を判断する材料が揃った」状態。自動で権限は広がらない |
| 物差し | 既存レビューの採点方式（往復コスト 0.6% 控除後の +1h/+4h/+24h フォワードリターン等、§2.2） |

## 2. 現状の裏取り（既存の仕組み）

本設計は新規の記録・採点基盤を作らず、既存の3つの仕組みに接続する。

### 2.1 判断の記録（strategy_decisions）

- 戦略は `RuleBasedStrategy.analyze(MarketContext)`（`packages/strategy-engine/src/index.ts`）が `TradingDecision` を返し、Worker の `analyzeCycle`（`apps/worker/src/engine.ts`）が毎サイクル（既定60秒）呼ぶ。
- 判断は `recordAnalysis`（`packages/database/src/index.ts`）経由で `strategy_decisions` テーブル（id＝cycleId、timestamp、json の汎用形）へ、指標スナップショット（`technical_indicators`）と同一トランザクションで保存される。
- 判断 json には `evidence`（StrategyEvidence）が含まれる：評価時刻、ローソク時刻、入力（価格、出来高、建玉価格、現在／前サイクルの指標値 ema20・ema50・rsi・macd・signal・histogram・atr・volumeChange・priceChange）、閾値（oversold、overbought、maxVolumeChange、stopLossPct、takeProfitPct 等）、条件充足（conditions：emaUp、rsiRecovery、histogramImproving 等の真偽）、選択ルール（selectedRule：BUY_SIGNAL、VOLUME_REJECT 等）。
- すなわち「ルールが何を見てどう判断したか」は既に凍結記録されている。影スナップショットはこの evidence を土台にする（§4）。
- 留意：ルール側の `confidence` は固定値（WAIT で 0、それ以外 0.7）であり、AI の confidence と尺度が違う。両者を直接比べない（§5）。

### 2.2 レビューの物差し（docker/run-review.py）

- export された DB の `strategy_decisions` を読み、Indexer の5分足で各判断のその後を測る。対象は +1h／+4h／+24h のフォワードリターン。
- 正味値は往復コスト 0.6%（手数料 0.3%/回、PAPER の feeRate 既定）を控除する。スリッページは未控除（実際はさらに不利側、と報告書に明記される）。
- 中核条件は emaUp・rsiRecovery・histogramImproving の3つ。充足数別のバケット、あと1つで買えた判断（充足数2＝ニアミス）の条件別内訳、仮想の利確 +1.5%／損切り −1.0% への先行タッチ（24h 以内）を数える。
- 事前登録バリアント（base＝現行ルール、novol、rsi45、shrink）を同じ物差しで採点する。影判断はこの表に「もう1つの候補生成器」として並ぶのが自然な接続点になる（§8）。
- フラグ閾値（判断材料が揃った合図）：標本 n ≥ 30、正味 +4h 平均 ≥ +0.30%、プラス率 ≥ 50%。注意側は正味 +4h 平均 ≤ −0.30%。
- 局面タグ（EMA50 の24h傾き ±0.5% で上昇／下降／横ばい）とボラ帯（ATR% ≥ 0.65 で高ボラ）の内訳もある。影の採点も同じ軸で分ける。
- レビューは証拠専用で、売買ルールを変えないことが冒頭に明記されている。影セクションも同じ立場を継ぐ。

### 2.3 公開 export のサニタイズ方針

- `deploy/paper-check/export_snapshot.py` はテーブル許可リスト（TABLES）方式で、テーブルごとに保持するフィールドを列挙し、数値・列挙値だけを通す。自由文は出さない（strategy_decisions でも `reason` は「settings/text, not public data」として明示的に除外）。
- manifest の `omitted` には settings、runtime、auth、market_candles、portfolio_snapshots、thresholds、free_text、raw_ids が並ぶ。
- 影の記録もこの方針に従う（§7.3）：構造化された数値・列挙は出してよいが、根拠の自由文とプロンプト本文は出さない。生のローソク列も market_candles と同様に出さない（採点はレビューが Indexer から引き直すため不要）。

### 2.4 ML 監査の段階基準との関係

`docs/ML_DATA_AUDIT_JA_20261107.md` の段階2（学習の試行が可能）は BUY候補300件以上・約定100件以上・閉じた往復80件以上が2局面以上に分散、を要求する。影判断は「約定」を生まないため、この基準の代用にはならない。影の卒業条件は §8.3 の通り別に事前登録し、ML 段階基準とは混同しない。

## 3. 全体像

```
tick（既存、そのまま）
  └─ analyzeCycle：ルール判断 → strategy_decisions へ記録（既存）
        └─ 影モジュール（新規、tick の外）
             1. トリガー判定（§6）… 発火しなければ何もしない
             2. スナップショット凍結（§4）… そのサイクルの入力をコピー
             3. LLM 呼び出し（非同期・単一飛行）… tick は待たない
             4. shadow_decisions へ追記（§7）… 成功も失敗も記録
レビュー（既存 run-review.py に影セクションを追加、§8）
  └─ 影BUY候補を既存の物差しで採点し、ルールの候補・ニアミスと並記
```

影モジュールは Worker 内の独立した部品とし、戦略・注文・安全系からは参照されない（依存は一方向：影が判断記録を読むだけ）。

## 4. 入力スナップショット（同一条件の凍結）

トリガー発火時に、そのサイクルの入力を凍結コピーする。内容は「その時点でルールエンジンが見たもの」と一致させる。

| 区分 | 内容 | 出所 |
|---|---|---|
| ローソク要約 | 直近 **50本（仮置き）** の5分足 OHLCV をそのまま凍結。加えて分析対象期間の高値・安値・始値からの変化率 | `MarketContext.candles` |
| 指標値 | 現在／前サイクルの ema20、ema50、rsi、macd、signal、histogram、atr、volumeChange、priceChange | evidence.inputs.current／previous |
| 条件充足 | conditions の真偽一式と充足数、ルール側の selectedRule と action | evidence |
| 板状態 | そのサイクル時点で Worker が保持する市場状態から、最良買い気配・最良売り気配・スプレッド・板の鮮度（取得時刻）を取る | Worker の市場状態（**新規に記録する項目**。現行 evidence には含まれない） |
| 保有・口座 | 建玉の有無、建玉価格（entryPrice）、当日買付累計など、そのサイクルの portfolio の要約 | evidence.inputs.entryPrice と portfolio |
| 設定 | そのサイクルで効いていた閾値（evidence.thresholds）と注文上限類（maxOrder 等） | evidence.thresholds と settings（ローカル記録のみ。export には出ない、§7.3） |
| 同定 | cycleId、ペア、candleTimestamp、evaluatedAt、スナップショットの sha256（同一入力の証明） | 記録時に付与 |

制約：

- AI へ渡すプロンプトは、この凍結スナップショットからのみ生成する。呼び出し時点の最新価格など、凍結後に得た情報を混ぜない（比較の公平性と再現のため）。
- スナップショットは影レコード内に保持し、後から市場データを引き直して「そのときの入力」を再構成しない。
- 対象は**保有なし（フラット）のサイクルに限る**。保有中の判断はルールの利確・損切りが専管であり、影の入口判断と混ぜない（出口判断への拡張は未決事項 §11-5）。

## 5. AI 出力スキーマ

AI には構造化出力（JSON）を要求し、スキーマ検証を通ったものだけを「判断」として記録する。

| フィールド | 型 | 内容 |
|---|---|---|
| action | 列挙 | `BUY` または `WAIT`（影の段階では SELL を出させない） |
| confidence | 数値 0〜1 | AI 自身の確信度。ルール側 confidence（0／0.7 固定）とは尺度が異なるため横並び比較はしない |
| rationale.refs | 配列 | 根拠の構造化参照：スナップショット内の事実を指す `{type, key, value}`（type は indicator／condition／candle／book／portfolio の列挙、key は該当フィールド名、value は観測値）。最大 **5件（仮置き）** |
| rationale.text | 文字列 | 根拠の短文。最大 **200字（仮置き）**。ローカル記録のみで export には出さない（§7.3） |
| model | 文字列 | 応答したモデル id |
| promptVersion | 文字列 | プロンプトの版数。版をまたいだ集計は分ける（§12） |
| latencyMs | 数値 | 呼び出しの所要時間 |
| usage | 数値群 | 入力／出力トークン数と、換算コスト（単価はプロバイダ決定後に固定） |
| calledAt | 数値 | 呼び出し時刻（epoch ms） |

スキーマ検証に失敗した応答（JSON でない、列挙外の action、参照がスナップショットに存在しない等）は判断として数えず、`status = ERROR` のレコードとして理由コードとともに記録する（§7.2）。部分的に壊れた出力を補完して判断に仕立てることはしない。

## 6. 呼び出し cadence（トリガー制）

毎ティック（60秒）呼ぶと 1日1,440回になり、コストとノイズの両面で過剰である。呼び出しはトリガー制にする。数値はすべて**仮置き**で、確定は未決事項 §11-2。

### 6.1 トリガー（いずれか成立で発火）

1. **ルール BUY 近傍**：中核3条件の充足数が 2 に達した、または前回評価時から充足数が増えた。
2. **ルール BUY 信号**：ルールの action が BUY になった（ルールが買う局面で AI が何と言うかは最重要の比較対象）。
3. **レジーム変化**：局面タグ相当（EMA50 の24h傾きの帯域、±0.5%）を跨いだ。レビュー側の定義と同一にする。
4. **最大間隔の経過**：最後の呼び出しから **15分（仮置き）** が過ぎた（局面が静かでも最低頻度のサンプルを確保するハートビート）。

### 6.2 抑制

- 最小間隔 **5分（仮置き）**：トリガーが連続してもこの間隔未満では呼ばない。
- 1日の呼び出し上限 **200回（仮置き）**：達したら当日は自動停止し、翌日の日次ロールオーバーで再開する（§9）。
- 保有中のサイクル、回復エピソード中（PAPER_NETWORK_PAUSED 等）や市場データが不健全なサイクルでは呼ばない。判断材料が欠けた状態での AI 判断は採点対象として意味を持たないためであり、安全系への配慮ではない（影はそもそも安全系に触れない）。

## 7. 保存方式

### 7.1 専用テーブル shadow_decisions

- `packages/database` の `eventTables` に `shadow_decisions` を追加し、既存テーブルと同じ汎用形（id TEXT、timestamp INTEGER、json TEXT）で持つ。
- id は cycleId とし、`strategy_decisions` の同サイクル行と 1:1 で結合できるようにする（レビューが両者を並べるための結合キー）。
- 追記は `db.append` の既存経路を使う。判断記録のトランザクションには混ぜない（影の失敗が判断記録を巻き込まないため）。

### 7.2 行の内容

| 区分 | 内容 |
|---|---|
| 同定 | cycleId、ペア、candleTimestamp、snapshotSha256 |
| 状態 | status：`OK`（判断が取れた）／`ERROR`（呼び出し失敗・スキーマ逸脱、理由コード付き）／`SKIPPED_BUDGET`（1日上限）／`SKIPPED_DISABLED`（kill switch 等） |
| 入力 | §4 のスナップショット凍結コピー |
| ルール側 | そのサイクルのルール action、selectedRule、条件充足数（並記用に複写。結合でも引けるが、行単体で読めることを優先） |
| 出力 | §5 の AI 出力一式（status が OK のとき） |
| 運用 | model、promptVersion、latencyMs、usage、calledAt |

トリガー判定の結果（発火しなかったサイクル）は記録しない。分母は「トリガー発火数＝レコード数」で数える。

### 7.3 公開 export への含有

- `export_snapshot.py` の TABLES に `shadow_decisions` を加え、専用の sanitize を書く。保持するのは数値・列挙のみ（2026-11-14：modelは `gpt-5.4-nano` のみ許可、詳細はDECISIONS_JA）：action、confidence、status、model、promptVersion、latencyMs、usage（トークン数・コスト）、スナップショットからは price・candleTimestamp・条件充足数・ルール側 action／selectedRule、そして rationale.refs（type／key は列挙照合、value は数値のみ）。
- **出さないもの**：rationale.text（自由文）、プロンプト本文、設定の値（thresholds 等）、生のローソク列、API キー（そもそも行に保存しない）。
- 根拠の自由文を将来 export に含めるかどうかは未決事項 §11-4（現方針は既存の free_text 除外に倣い出さない）。

## 8. 採点（run-review の影セクション）

### 8.1 採点方法

`docker/run-review.py` に影セクションを追加する。影レコード（status = OK）を export DB から読み、ルール判断と同じ物差しで測る：

- 影 BUY 候補について +1h／+4h／+24h フォワードリターン（素と正味＝往復 0.6% 控除後）、平均・中央値・プラス率。
- 仮想タッチ（利確 +1.5%／損切り −1.0%、24h 以内、先行の別）も影 BUY に同じく適用する。
- 局面タグ・ボラ帯の内訳も既存と同じ軸で分ける。

### 8.2 並記と比較

- 影 BUY 候補の成績を、事前登録バリアント表（base／novol／rsi45／shrink）と同じ表に1行加えて並べる。
- 一致／不一致の内訳を出す：AI のみ BUY、ルールのみ BUY（base 候補）、両者 BUY、両者 WAIT の4区分と、各区分の正味 +4h。特に「AI のみ BUY」はルールが見送った局面での AI の値打ちそのものであり、卒業判定の主対象とする。
- レポート冒頭の立場（証拠専用、売買ルールは変更しない）は影セクションにも適用する。

### 8.3 卒業条件（事前登録）

以下をすべて満たしたとき「卒業」とし、権限拡大を判断する材料が揃った合図とする。数値は**仮置き**（確定は未決事項 §11-3）だが、既存のフラグ閾値と ML 段階基準の考え方に合わせてある：

1. 「AI のみ BUY」候補が n ≥ **30**（既存フラグの FLAG_MIN_SAMPLES と同値）。
2. その正味 +4h 平均 ≥ **+0.30%**、プラス率 ≥ **50%**（既存フラグ閾値と同値）。
3. 候補が局面タグ（上昇／下降／横ばい）の **2局面以上** に分散している（1つの相場つきへの偏りを卒業と認めない）。
4. 同一期間・同一物差しでのルール base 候補の正味 +4h 平均を下回っていない。

卒業しても権限は自動では広がらない。卒業は「次の判断（§10 段階 S3）をする材料が揃った」という合図にすぎない。

### 8.4 採点の限界（明記）

影の BUY は約定の現実を通らない：スリッページ、板の薄さによる不約定、ProfitGuard の棄却は経験しない。正味値は手数料のみ控除した近似であり、実弾ではさらに不利側になる。これは既存のニアミス採点と同じ限界で、卒業判定はこの近似の範囲での話である。

## 9. 安全設計

| 観点 | 設計 |
|---|---|
| tick との分離 | 影の呼び出しは tick のクリティカルパスの外（判断記録の後にキューへ投入し、非同期に処理）。tick は LLM の応答を待たない。同時実行は1件まで（単一飛行）。タイムアウト **30秒（仮置き）** |
| 失敗時 | 例外は影モジュール内に閉じ、ERROR レコードを残してスキップする。連続失敗しても Worker の安全系・回復系には何も伝播しない。リトライはしない（次のトリガーを待つ） |
| kill switch | 環境変数 `SUIBA_SHADOW_ENABLED`。未設定または false のとき完全無効（スナップショット凍結すらしない）。既定は無効で、明示的に有効化したときだけ動く |
| コスト上限 | 1日の呼び出し上限（§6.2）に達したら当日は自動停止する。日次カウンタは portfolio の日次ロールオーバーと同じ JST 日キーで永続化し、再起動で上限が復活しないようにする |
| API キー | ホストの環境変数（例：`SUIBA_SHADOW_API_KEY`）でのみ保持する。設定 DB・影レコード・ログ・export のいずれにも値そのものを書かない |
| 記録の保全 | 影レコードは追記のみ。プロンプト改訂時は promptVersion を上げ、旧版のレコードを書き換えない |

## 10. 段階と順序

- **前提**：本番切替（24h 検証の卒業後）と集中観察週間での安定化が先。影は本番の PAPER データで回す方が価値が高い（検証ランは期間が短く局面が偏る）ため、実装着手は本番安定化の後とする。
- **段階 S1（記録基盤）**：スナップショット凍結、トリガー判定、専用テーブル、export の sanitize、LLM 接続を実装する。まず呼び出し頻度とコストの実測を取り、cadence の仮置きを確定値へ寄せる材料にする。
- **段階 S2（採点）**：run-review の影セクションを実装し、日次レビューと並走させる。卒業条件は事前登録のまま動かさない。
- **段階 S3（本書の範囲外）**：卒業後、権限を広げるかどうか・どの範囲かをオーナーが判断する。権限を渡す先は TradeCap 設計（`docs/REAL_TRADING_TRADECAP_DESIGN_20261025.md`：売買のみ・出金不可・失効可能）の枠組みで扱い、本書では決めない。

TradeCap Phase 1（testnet）との関係：影は PAPER 本番の記録系、Phase 1 は testnet の執行系で、対象が重ならないため独立に進められる。ただし実装着手はどちらも本番安定化の後であり、順序は本番切替 → 安定化 →（影 S1／Phase 1 は並行可）とする。

## 12. リスク一覧

| リスク | 内容 | 緩和策（本設計内） |
|---|---|---|
| コストの暴走 | トリガー誤判定や局面の荒れで呼び出しが増える | 最小間隔、1日上限での自動停止、kill switch（§9） |

| プロンプト変更による断絶 | 版が変わると成績が連続しなくなる | promptVersion を記録し、版をまたぐ集計を分ける。変更は版上げとして扱う |
