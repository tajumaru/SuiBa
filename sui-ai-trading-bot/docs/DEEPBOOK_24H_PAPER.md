# DeepBook 24時間PAPER検証（Windows 11）

この環境は `167ede8` のDeepBook Provider・根拠付き5分足再構築・運用検証を再利用します。取引ロジック、RiskEngine、Profit Guard、GeckoTerminalの既定値を変更しません。今回実装するのは検証環境と計測です。**実際の24時間試験は利用者が開始します。短時間のDocker試験や合成データによる集計テストは、24時間稼働の完了証明ではありません。**

## 分離されるもの

| 項目           | 専用環境                                                                            |
| -------------- | ----------------------------------------------------------------------------------- |
| Compose        | `docker/compose.deepbook-24h.yaml`（既存Composeを継承しない）                       |
| プロジェクト   | `suiba-deepbook-24h`                                                                |
| ブラウザー     | `http://127.0.0.1:3101`（既存3100とは別）                                           |
| SQLite         | `/app/validation/deepbook-paper.sqlite`                                             |
| 永続ボリューム | `suiba-deepbook-24h_validation-data` / `suiba-deepbook-24h_validation-reports`      |
| 設定           | `docker/.env.deepbook-24h`                                                          |
| 管理トークン   | `docker/secrets/deepbook-24h-admin.txt` → Docker secret（環境変数の値には入れない） |
| Dockerログ     | 専用コンテナのjson-file、10MB×3。`logs`でホストに時刻付き保存                       |
| 自動レポート   | `/app/reports/latest.json` / `latest.md`、約60秒ごと・正常終了時に更新              |
| ホスト出力     | `docker/artifacts/`（Git・Dockerビルド対象外）                                      |

Composeが `MODE=PAPER`、`MARKET_DATA_PROVIDER=deepbook`、`DEEPBOOK_RECONSTRUCT_CANDLES=verified` を固定します。専用フラグ有効時には、専用DBパス・PAPER・DeepBook・verifiedの組み合わせをWorkerも検査します。LIVEは起動前に拒否します。秘密鍵、署名、BalanceManager、実資金は不要です。GeckoTerminalへのフォールバックはこのプロファイルでは行いません。

既存の `.env`、SQLite、`paper-data` ボリューム、稼働コンテナを変更・停止しません。以下のヘルパーは常に専用プロジェクト名・専用Compose・専用envを指定します。**ボリューム削除コマンドは使用しないでください。**

## 初回セットアップ

Docker Desktopを起動し、LinuxコンテナでEngineが実行中であることを確認します。Node.js 24も必要です。WindowsのスリープとDocker Desktopの手動一時停止・Resource Saverが24時間試験を中断しないようにし、電源接続と十分なDockerディスク空き容量を確認してください。必要ディスク容量は修復証拠量・周期に依存します。開始前と終了後に `docker system df` を確認し、空き容量不足時にデータを削除して続行しないでください。

PowerShellで、この変更を含むチェックアウトのプロジェクトへ移動します。配置例:

```powershell
Set-Location D:\Source\SuiBa\sui-ai-trading-bot
node --version
docker version
node docker/deepbook-24h.mjs init
```

`init`は専用envとランダムな管理トークンだけを作成します。既存ファイルは上書きしません。本番の `.env` をコピーしないでください。

必要なら `docker/.env.deepbook-24h` をテキストエディターで編集します。初期値はポート3101と公開Sui Mainnet gRPCです。ポート競合時は `VALIDATION_PORT=3102` など空きポートを指定します。変更後のURLもそのポートになります。APIキー付きURLを使う場合はこのGit対象外ファイルだけに保存し、画面・ログ・コミットへ貼り付けないでください。取引秘密鍵は設定しません。管理トークンファイルも共有フォルダーに公開しないでください。Windowsでは保存フォルダーのNTFSアクセス権を自分のアカウントに限定してください。

```powershell
node docker/deepbook-24h.mjs up
```

これはビルドして**専用コンテナのみ**を起動します。Botは停止状態です。`http://127.0.0.1:3101` を開き、専用トークンファイルをエディターで開いて、内容を管理トークン欄へ貼り付けて接続します。トークンをチャットやログへ出力しないでください。

## 計測開始とPAPER運用開始

1. ダッシュボードで安全重視の設定とProfit Guard有効を確認します。Workerの標準待機周期は60秒です。試験中は設定を変えないでください。
2. Bot停止状態のまま、Sui gRPC・DeepBookの正常取得とローソク足品質を確認します。最初の根拠照会には時間がかかる場合があります。異常がある状態で計測を始めないでください。
3. 「運用検証」→「DeepBook 24時間PAPER検証」→「24時間計測を開始」を押します。代わりに次のコマンドも使用できます。

```powershell
node docker/deepbook-24h.mjs begin
```

4. **計測開始から30秒を目安に**、既存画面から明示的にPAPER運用を開始してください。計測開始だけでは売買は開始しません。24時間PAPER実稼働の許容差は45秒なので、長く待ってから開始した試験は合格になりません。
5. 開始時刻・計測ID・24時間の進捗が表示されることを確認します。ブラウザーを閉じてもWorkerが計測します。

一度開始した計測は再起動しても同じIDで続きます。`begin`の再実行は409で拒否し、既存記録をリセットしません。やり直すときも既存DBを削除しないでください。まずレポート・停止時バックアップを保存し、次の試験は別のComposeプロジェクト名・ポート・env/secretファイルで分離してください。その場合、上記の固定プロジェクト用ヘルパーを混在させず、その試験の明示的なComposeコマンドを使ってください。

## 途中確認と出力

```powershell
node docker/deepbook-24h.mjs status
node docker/deepbook-24h.mjs report
node docker/deepbook-24h.mjs logs
```

`report`は `docker/artifacts/deepbook-24h.json` と `.md` に保存します。認証はコンテナ内でsecretを読み込んで行い、トークンをコマンド引数へ展開しません。画面にもJSON・Markdownの保存ボタンがあります。

内部のSQLite `validation_events` には、APIの実試行、15秒の状態記録、Worker周期の結果、約定時の安全証拠を追加保存します。24時間分を200件などで切り捨てず集計します。追加の市場APIポーリングは行いません。キャッシュ利用・同時要求の集約はリクエスト件数に加算しません。API成功率はHTTP/通信成功率で、JSON内容・板・足の品質は別の周期正常率で評価します。

平均/P95は実試行の完了（レスポンス本文受信まで）の所要時間です。HTTP 429/502/503/504、タイムアウト等をコード別に保存します。APIの接続状態・バックオフ・次回再試行時刻は既存のAPI監視も参照してください。Indexer遅延と板数量は既存取得結果を使用します。

5分足は、UTC時刻で重複を除いた使用可能足・欠損・再構築・未解決数を表示します。最新生データ本数と、未解決足を観測した取得周期・延べ足数もJSONに保存します。同じ古い欠損を次の周期にも観測するため、延べ数を固有の欠損数と混同しないでください。再構築の取得元・取得時刻・理由・証拠パスはprovenanceを保存します。過去の失敗は後から修復されても失敗履歴に残ります。

AI内訳は、実行された既存戦略の生のBUY/SELL/WAITです。データ不足で分析前に停止した周期は分析回数に加算しません。PAPER注文記録（拒否を含む）とPAPER約定を区別します。損益は最後の記録で評価できた資産額と計測開始資産額の差です。評価価格がないSUI残高があれば未評価になります。

## 合格条件と運用基準

- 24時間到達前は常に **検証途中**。24時間到達後も条件不足は **要確認（合格条件未達）**。判定だけを理由に標準Providerを切り替えないでください。
- 計測保存失敗・正常終了を確認できない強制終了は整合性エラーとして保持し、合格にしません。再起動後も記録は継続します。
- 記録は15秒ごと。45秒を超える空白は不合格。計測IDを保持することと連続稼働に合格することは別です。
- PAPER実稼働が24時間に達すること（45秒の許容差）。停止中も通信確認・計測は続きますが、PAPER実稼働時間には加算しません。
- DeepBook実試行成功率99%以上、API P95がWorkerの待機周期未満。周期数は `24時間÷（待機周期+45秒）` 以上、周期正常率99%以上。これは運用評価用で、取引安全条件の緩和ではありません。
- 既存の板鮮度10秒、Indexer遅延60秒、確定5分足鮮度360秒、設定スプレッド・注文額内の両方向流動性、見積もり有効期限を維持します。再構築の上限45秒、未解決欠損ゼロを要求します。
- 約定の同一トランザクションに保存する足・板・見積もり期限・PAPER状態・RiskEngine/Profit Guard承認証拠と、約定件数が一致すること。足の妥当性を集計時にも再検査します。
- API障害時の停止（すでに安全停止中の再試行は停止状態を確認）、停止後の自動再開なし、Profit Guard常時有効・周期不変・分析実行あり。
- 約定やAPI異常が0件なら、その安全経路は **未行使** と表示します。合成データ・障害注入テストと、実環境で観測した結果を区別してください。実資金移動の独立したチェーン監査は行いません。

24時間後に `status` と `report` を取得し、全条件とAPI障害・欠損・停止履歴を確認してください。計測窓は開始から24時間で固定されます。24時間経過によるBotの自動停止・自動再開はありません。終了する場合は明示的に停止します。

## 停止・再起動・異常時

通常停止・緊急停止は既存画面の操作を使います。API障害や未解決欠損があれば安全停止が維持されます。429の待機・再試行上限を解除して回避しないでください。接続回復だけではBotを再開しません。理由・API再試行時刻・足/板品質を確認して、必要なリセットと手動開始を行います。自動再開スクリプトを作らないでください。

```powershell
node docker/deepbook-24h.mjs stop
node docker/deepbook-24h.mjs restart
```

`stop`は専用コンテナだけを安全終了します。停止したコンテナを起動する場合も `up` を使えます。再起動時はBot停止、緊急停止・異常理由と計測IDを保持します。手動再開まで取引しません。再起動に伴う記録の空白やPAPER停止時間も評価対象です。

ディスク不足・計測保存失敗時は処理を続けず、Workerが終了または安全停止します。再起動してもPAPERを自動再開しません。計測記録不足は合格になりません。容量不足を解決する際も既存DB・履歴・ボリュームを削除しないでください。

停止状態でDBディレクトリ全体（残っているWAL/SHMを含む）とレポートをバックアップできます。

```powershell
node docker/deepbook-24h.mjs backup
```

`docker/artifacts/backup-日時/` に保存し、Botを停止したままにします。稼働中にSQLite本体だけをコピーしないでください。ホストのバックアップ先容量にも注意してください。Docker Desktop更新・イメージ更新前も、レポート・ログ・停止時バックアップを取得します。更新中の空白を24時間の正常記録として扱いません。

## 開発者向け検証

```powershell
pnpm build
pnpm test
pnpm test:e2e
node docker/verify-deepbook-24h.mjs
```

最後のコマンドはランダムな専用テストプロジェクト、別secret、別ボリューム、空きローカルポートを使用します。外部APIはローカルの到達不能Sui接続へ置き換え、DeepBookへ負荷をかけません。認証・計測開始・部分レポート・WAL・SIGTERM再起動・履歴/緊急停止保持・LIVE起動拒否を確認します。終了後テストコンテナを停止・除去しますが、テストボリュームは削除せず名前を表示します。実際の24時間・Mainnetの成功率や可用性の測定にはなりません。

既存Composeの回帰試験は `node docker/verify-compose.mjs <検証イメージ名> --browser` です。別のランダムなComposeプロジェクトを使い、Linuxユニットテスト、認証済みブラウザー、WAL、バックアップ、強制再起動、LIVE拒否、ディスク満杯時の安全性を確認します。本番環境には接続しません。

実装時に実行したテストと未実施項目は [検証結果](DEEPBOOK_24H_VALIDATION_RESULTS.md) を参照してください。
