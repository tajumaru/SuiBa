# PAPER運用検証 1.0

基準: 最新main `268427a`。実売買・秘密鍵・署名・送信は追加しない。

## 追加した機能

ダッシュボードの「運用検証」は認証付き `GET /api/operations` から取得する。既存の `/api/state`、設定スキーマ、開始停止APIの契約は維持する。

監視開始からのPAPER稼働時間、最終市場データ/見積もり/約定/正常処理時刻、最終BUY/SELL/WAIT、利益保護・リスク制限による拒否、APIエラー・連続エラーを表示する。停止中、正常稼働、データ遅延、異常停止を区別する。画面の取得失敗時には古い記録を正常稼働の現在値として表示しない。

- 稼働時間は手動開始から停止まで。通常は15秒ごとの確認で永続化し、不意の再起動によるオフライン時間を加算しない。クラッシュ直前の未確認の最大15秒程度は含まれない。
- APIエラーは市場・見積もり・Suiヘルスの論理取得処理の失敗数。SDK内部の個々の再試行回数ではない。連続エラーは正常な取得・処理周期が完了するとリセットするが、Botの停止は解除しない。
- 最終アクションは約定BUY/SELLと、戦略WAIT/拒否後のWAITを集計。表示だけの利益試算を拒否件数に数えない。
- Profit Guardで拒否された候補のRiskEngineは「未評価」。評価していないものを許可/拒否として記録しない。

## 記録・後方互換性

SQLiteに `operation_candidates`、`operation_events`、`paper_checks` と検索用インデックスを追加する。`CREATE TABLE/INDEX IF NOT EXISTS` の追加専用移行で、既存テーブル・設定・履歴を削除/書換えしない。監視状態は既存KV領域の専用キーに保存する。

売買候補は見積もり取得前にPENDINGとして保存し、方向・要求入力・SUI予定数量・見積もり価格・期限・原価・予想売却額・費用・利益条件・両ガード・最終アクションを記録する。BUYの予想売却額は現在の逆方向見積もりに基づく想定利確時の試算であり、将来の価格や利益を保証しない。分割売却を想定する費用・ガスも別に記録する。DEX費用の内訳不明は0に置き換えず、見積もり内に含む費用を重複加算しない。

新しい約定・成功した独立照合・候補の最終結果・約定後評価は同じDBトランザクションで保存する。再起動時に残っているPENDINGは中断として閉じ、約定には変換しない。

新規記録に認証ヘッダー、管理トークン、環境変数、秘密鍵、任意の上流例外文字列、URLを保存しない。エラーは許可されたコードに置き換える。

## 会計照合

既存 `PaperTrading.fill`、Profit Guard、RiskEngineの計算・制限を変更せず、別のDecimal計算で約定の前後を照合する。USDC、SUI、原価、部分売却の按分原価、実現/未実現損益、手数料、今回のガス、実行時設定から再計算した費用、総資産評価、損益変化を確認する。累計ガスは照合記録の期待値合計と約定記録を比較し、累計手数料・原価・残高も最後の成功した照合と突き合わせる。

- SUIは9桁: 許容誤差 `0.000000001 SUI`。
- USDCは6桁: 許容誤差 `0.000001 USDC`。
- 総資産/評価損益は `0.000001 USDC + 評価価格 × 0.000000001 SUI`。
- SUI最小単位文字列は完全一致も確認する。
- 部分売却の原価は既存処理と同じくUSDC6桁で切上げ配分する。残り原価・数量も検証する。
- 旧約定の不明ガス/DEX費用は不明のままとし、判明分の小計と照合未導入の件数を区別する。
- 旧ポジションの開始残高を捏造しないため、約定前後の損益変化を照合する。導入前の履歴を遡って完全照合できるとは表示しない。

約定候補の照合が失敗した場合は約定を保存せず、失敗記録を残して安全停止する。保存後/後続周期での残高・費用記録の不整合も停止対象にする。既存の重複制約と、コミット直前の停止・緊急停止確認を維持する。

## 異常検出と停止

既存の取得エラー時の即時停止を維持する。連続3回のAPI失敗も検出するが、元の即時停止を3回まで待つようには弱めない。市場データは既存の確定足検証を再利用し、15秒ごとの監視で360秒以上の更新/確定足停止も検出する。見積もりは既存の15秒以内の有効性検証を継続する。期限切れ、取得失敗、重複、残高不足、原価・費用不明、会計不整合、日次損失制限を記録する。

日次損失到達や通常のProfit Guard/RiskEngine拒否は記録・購入拒否とし、既存の保護的SELLを妨げる全停止に変更しない。見積もり・数量・費用検証を免除することもない。古い過去の見積もりが表示されているだけでは約定せず、実行候補で再確認する。

停止・再起動・正常な取得への復帰だけで自動開始しない。異常原因を確認して手動で停止解除し、開始は別途実行する。

設定の取得間隔が長い場合も市場の鮮度制限は緩めない。継続検証は既定の60秒間隔を基本とし、180秒以上取得がない状態をデータ遅延、360秒以上を安全停止の目安とする。

## 24時間・7日間レポート

約定回数、売却単位の勝率、評価損益を含む純損益、最大ドローダウン、両ガードの見送り、エラー、異常、停止理由を表示する。期間開始前の直近評価を基準にする。存在しない場合は期間内最初の評価との比較となり、比較開始時刻を表示する。取引ゼロ件も正常な観測結果で、勝率は「売却なし」。足りない評価情報は未評価にする。

期間集計はタイムスタンプ付きDB検索を用い、既存の履歴画面用200件/10000件の上限で切らない。監視導入前の拒否/エラーの完全な集計はできないため、監視開始時刻と部分期間を明示する。運用条件を自動変更する処理はない。

## Windows 11 / Docker Desktop での実市場検証手順

前提: LinuxコンテナモードのDocker Desktop/Composeと、インターネットへのHTTPS接続。Docker未導入の環境で長時間Workerを自動起動しない。

```powershell
cd sui-ai-trading-bot
# 既存.envを上書きしない
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
# .envをエディターで開き、ADMIN_TOKENに32文字以上の値を設定する。
# トークンをログ、チケット、Gitへ貼らない。
docker compose -f docker/compose.yaml config --quiet
docker compose -f docker/compose.yaml up -d --build
docker compose -f docker/compose.yaml ps
```

1. `http://127.0.0.1:3100` で管理トークンを使って接続する。
2. 初回起動とコンテナ再起動直後は停止中。市場データの取得を待ち、「運用検証」で取得時刻と異常がないことを確認する。
3. 設定画面で安全重視の予定値を確認し、明示的に適用する。既存設定を使う場合はカスタムの値を確認する。保存だけでは起動しない。
4. 「PAPER運用開始」を押す。実資金は使わず、既存戦略・Profit Guard・RiskEngineを通過した候補のみ仮想約定する。
5. 24時間/7日後にレポートを確認する。実際の観測期間が足りなければ部分期間表示になる。取引がなくても正常で、利益条件を下げない。
6. 異常停止時は理由を確認する。429ならAPI側の制限・取得頻度を確認して待ち、正常取得を確認後に手動解除・手動開始する。自動復帰はしない。

### 永続化・再起動・ログ

`paper-data:/app/data` にSQLite本体・WAL・設定・全履歴・監視記録を保存する。既存と同じvolumeを再利用する。既存で特別なDATABASE_PATHを使用していた場合は、切り替え前に実際のファイルを保全し、同じ永続領域で使用する。composeは標準の `/app/data/bot.sqlite` を指定する。`down -v` やvolume削除は履歴を失うため行わない。

```powershell
docker compose -f docker/compose.yaml restart bot
# 再接続し、停止中で設定・履歴が残っていることを確認してから手動開始する。
docker compose -f docker/compose.yaml logs --tail 50 bot
```

ヘルスチェックは `/healthz` の応答と15秒の監視ハートビートを検査する。Botの安全停止はコンテナの故障と区別し、停止中でも正常なプロセスはhealthyとする。認証なしのヘルス応答にはPAPERモードとプロセス状態だけを含める。

ログはDockerのjson-fileドライバで10MB×3ファイルにローテーションする。認証情報をstdoutへ出さず、ヘルスチェックにもトークンを渡さない。設定や履歴であるSQLite記録は自動削除しないため、ディスク容量とバックアップは運用側で管理する。Docker公式の[ヘルスチェック仕様](https://docs.docker.com/reference/compose-file/services/#healthcheck)・[ログローテーション仕様](https://docs.docker.com/engine/logging/drivers/json-file/)を参照。

### Dockerを使わない短時間の確認

```powershell
pnpm install --frozen-lockfile
pnpm build
pnpm test
pnpm exec playwright install chromium
pnpm run test:e2e
pnpm smoke
pnpm run verify:runtime
```

`smoke` は実gRPC・5分足・両方向見積もりの読み取りだけ。`verify:runtime` は専用の一時DBを使用し、取引停止中で5分・15分・1時間の3種類の足・API・再起動を検証する。上流429などがあれば成功扱いにせず失敗する。API制限を避けるため、これらの実市場確認を同時・高頻度には実行しない。

- 初回実装時はDocker未導入でしたが、追加検証でDockerビルド・Compose起動・volumeマウント・コンテナ再起動/再作成・停止/緊急停止/履歴保持を確認しました。詳細は[API安定化・Docker運用 1.1](API_DOCKER_V1_1.md)を参照してください。
- 実機Safari、連続24時間/7日間の実相場運用、停電/ホスト全体のディスク満杯/大規模履歴の耐久検証は未実施。レポートの期間集計は合成時刻と250件以上の履歴で検証する。
- 24時間/7日間の市場稼働が成功したと示すデータは捏造しない。
- APIの429/停止・市場の流動性不足で安全停止や見送りが起こり得る。収益性は保証しない。



## 実施した検証

- `pnpm build`: 型検査・本番ビルド成功。既存Zodのpure注釈警告のみ。
- `pnpm test`: 10ファイル・142件成功（追加の運用検証24件、LIVE起動拒否1件、既存Profit Guard/RiskEngine/バックテスト/PAPER APIを含む）。
- `pnpm run test:e2e`: 48件成功。既存の設定画面28件と運用検証20件を375/390/430/1280pxで実行。停止/正常/遅延/異常、取引ゼロ、候補明細、誤差表示、通信エラー時の古い正常表示抑止、横はみ出しと操作領域を確認。
- `pnpm smoke`: 実gRPC、実SUI/USDCプール、5分足999本、BUY/SELL両方向の有効な価格見積もりを取得。署名・取引送信なし。
- `pnpm run verify:runtime`: 初回は上流HTTP 429で安全停止して失敗を報告。時間を置いた再試行では実市場の5分・15分・1時間足、指標、認証API、緊急停止・再起動時の停止保持が成功。外部APIの制限も未解決の運用リスクとして残る。
- 実運用DBはテストに使用せず、一時DB/専用検証DBで検証。新しい監視記録以外の既存履歴を削除しない。
